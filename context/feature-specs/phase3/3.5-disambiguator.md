# 3.5 — Disambiguator

**Modules:** `pipeline/disambiguator/disambiguator.py`, `pipeline/disambiguator/prompts.py`
(+ `__init__.py`)
**Depends on:** 0.1 (`SchemaMapping`, `AmbiguityResult`, `CandidateMapping`, `EntityLookupResult`,

**Consumed by:** 3.6 (Query Generator reads `SchemaMapping.cypher_syntax`); orchestrator
(commits, tracks `previously_tried`, drives the semantic-mismatch retry).

---

## Objective

Commit to exactly **one** interpretation of an ambiguous question by selecting the most
contextually appropriate candidate, emitting a structured `SchemaMapping` whose `cypher_syntax`
is injected into the Query Generator. Automated mode is fully built; interactive (EIG-based)
mode is a documented interface stub (the Gradio demo, 6.2, implements it).

`(question, ambiguity_result, candidate_mapping, entity_lookup, dis_llm, previously_tried,
mode="automated") → Optional[SchemaMapping]`  (None = all candidates exhausted)

> **Format contract (load-bearing).** `cypher_syntax` is what the QG consumes, and the QG was
> trained on `extract_schema_pattern`-format committed patterns (1.1/1.3). The few-shot examples
> steer the LLM to that exact style (`(p:Person)-[:SUSPECTED_OF]->(i:Incident)`,
> `(p:Person)-[:OWNS {active:true}]->(v:Vehicle)`). Keep them consistent; if QG quality reveals a
> mismatch, fix it here/0.1, not in the QG, and record it in `decisions-log.md`.

from pipeline.ambiguity.prompts import _format_candidate_block, _format_entity_block
from pipeline.types import AmbiguityResult, CandidateMapping, EntityLookupResult, SchemaMapping

DIS_SYSTEM_PROMPT = """\
You are a disambiguation engine for a police knowledge graph query system. You receive a
natural-language question identified as ambiguous, plus the candidate schema mappings from the
Schema Linker. Commit to exactly ONE interpretation by selecting the most contextually
appropriate mapping, and output a single committed Cypher pattern for the query generator.

The schema is the POLE schema from the Ambiguity Detector system.

## How to Choose
- Use the question's linguistic context to pick the most informative interpretation.
- SCHEMA: choose the relationship type most consistent with the phrasing and investigative context.
- ENTITY: if the question gives identifying features (role, location, case) use them; else commit
  to the most common reading.
- INTENT: choose the reading that returns the most useful structured result (prefer specific).
- TEMPORAL: default to current state (active:true) unless the question is past-tense
  ("has owned", "used to live") or explicitly requests history.

1. The original question (unchanged). 2. The ambiguity type. 3. The candidate distribution
(Cypher syntax + scores). 4. Entity lookup results. 5. Previously tried mappings — do NOT repeat.

{"committed_pattern": "(p:Person)-[:SUSPECTED_OF]->(i:Incident)", "rationale": "..."}

## `disambiguator.py` — the stage

```python
# pipeline/disambiguator/disambiguator.py
from __future__ import annotations

import json
from typing import Optional

from pipeline.disambiguator.prompts import DIS_SYSTEM_PROMPT, build_disambiguator_prompt
from pipeline.llm import BaseLLM, GenerationConfig
from pipeline.types import (AmbiguityResult, CandidateMapping, EntityLookupResult,
                            ResolutionMode, SchemaMapping)


def disambiguator(
    question: str,
    ambiguity_result: AmbiguityResult,
    candidate_mapping: CandidateMapping,
    entity_lookup: EntityLookupResult,
    dis_llm: BaseLLM,
    previously_tried: list[SchemaMapping],
    mode: ResolutionMode = "automated",
) -> Optional[SchemaMapping]:
    """Commit one interpretation. Returns None if all candidates have been tried.

    automated: prompt dis_llm, parse {committed_pattern, rationale}; null pattern → None.
    interactive: raise NotImplementedError — the interactive contract (pose a clarification
      question, await a reply) is implemented by the Gradio demo (6.2); the evaluation harness
      uses automated only.
    """
    if mode == "interactive":
        raise NotImplementedError(
            "Interactive disambiguation is a documented extension; see the Gradio demo (6.2). "
            "The evaluation harness uses automated mode."
        )
    prompt = build_disambiguator_prompt(
        question, ambiguity_result, candidate_mapping, entity_lookup, previously_tried,
    )
    completions = dis_llm.generate_chat(
        [{"role": "system", "content": DIS_SYSTEM_PROMPT},
         {"role": "user", "content": prompt}],
        GenerationConfig(max_new_tokens=256, do_sample=False),
    )
    return _parse_disambiguator_output(
        completions[0].text, question, candidate_mapping, previously_tried,
    )

> handle it. Flagged: if such readings degrade QG output, consider constraining the

## Edge cases

| Situation | Behaviour |
|---|---|
| LLM returns `committed_pattern: null` | return `None` (orchestrator: candidates exhausted) |
| LLM repeats a previously-tried pattern | fall back to best untried candidate; `None` if none left |
| Malformed JSON | deterministic fallback to best untried candidate; `None` if exhausted |
| `detected_types` empty ("unknown") | still disambiguate; the prompt says type "unknown" |
| `mode="interactive"` | `NotImplementedError` pointing to 6.2 |
| `previously_tried` non-empty | rendered in the prompt; honoured for the fallback too |

`previously_tried` lifecycle (orchestrator-owned, per 0.1, AMENDED 2026-06-10): accumulates across
disambiguation retries AND Schema Linker outer-loop retries — the deterministic linker reproduces
the same candidate set on re-link, so the list persists for the whole run. It is never cleared.

## Acceptance criteria

Now (no GPU; LLM call deferred):
1. `_format_tried_block([])` → `""`; with two mappings → the "DO NOT repeat" block listing both
   `cypher_syntax` strings.
2. `build_disambiguator_prompt` includes the question, the `Ambiguity type:` line, the candidate
   block, the entity block, and (when present) the tried block.
3. `_parse_disambiguator_output('{"committed_pattern": "(p:Person)-[:SUSPECTED_OF]->(i:Incident)",
   "rationale": "x"}', …)` → a `SchemaMapping` with that exact `cypher_syntax`,
   `resolution_mode="automated"`.
4. `committed_pattern: null` → `None`. A pattern equal to a `previously_tried` entry → fallback to
   the next best untried candidate (or `None`).
5. `mode="interactive"` raises `NotImplementedError`.

Deferred (LLM): end-to-end selection on ambiguous benchmark questions; DSR computed in 4.2.

## Handoff

`disambiguator(...) → Optional[SchemaMapping]`. The orchestrator: on a `SchemaMapping`, appends it
to `previously_tried`, sends `cypher_syntax` to the Query Generator (3.6); on `None`, ends the
disambiguation loop (failure or fall back per 5.2). The interactive stub's contract is the
clarification-question path that 6.2 builds.
