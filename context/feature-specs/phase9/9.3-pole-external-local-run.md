# 9.3 — External POLE Benchmark: Pipeline Integration + Local API Run

**Modules:** `pipeline/schema.py` (additive), `pipeline/entity_lookup/registry.py` (additive),
`pipeline/ambiguity/prompts.py` + `pipeline/disambiguator/prompts.py` (additive), `experiments/run_evaluation.py`
(`resolve_dataset` third branch), `config/pipeline_pole_external.yaml` (new — separate from the
shared `config/pipeline.yaml`), `experiments/analyze_qualitative.py` (reused unmodified).
**Depends on:** 9.2 done (canonical `data/benchmark-pole-external.json`). Live external POLE
Neo4j (same instance/contract as 9.2). `ANTHROPIC_API_KEY` for the local run. **No GPU.**
**Consumed by:** the dissertation (Phase 9 completion evidence). Optional future Kaya run.

---

## Objective

Make the whole pipeline run against the external POLE benchmark **by config only**, mirroring
7.3's "one switch, everything else untouched" pattern — v2 and v3 stay byte-identical, this is a
third, additive, config-selected dataset. Then run the full three-condition evaluation (C1/C2/C3)
**locally**, using an API model (not Kaya, not GPU), and produce both the standard tables/metrics
artefacts and the qualitative comparison artefacts (`qual_records_*.json` +
`qualitative_analysis_*.md`) that the 2026-07-27 follow-up added for v3 — so this supplementary
external-validity check gets the same depth of evidence the primary v2/v3 results already have,
not just headline numbers.

**Framing (carried from 9.1/`project-overview.md`):** this is a supplementary external-validity
check. v2/v3 stay frozen and remain the primary evaluated benchmarks; nothing here touches them.

---

## Why a new config file, not `config/pipeline.yaml`

`config/pipeline.yaml` is the shared, actively-used config for the v2/v3 work (currently pointed
at `dataset_version: v3`, `active_model: claude-sonnet`, `results_tag: v3_localdb` — an in-flight
local rerun). Per 7.3's own convention of isolating a specific run variant into its own file when
it isn't meant to become the new shared default (e.g. `config/pipeline_v3_qgprops.yaml`), this
step's config lives in **`config/pipeline_pole_external.yaml`**, a full standalone copy of the
`pipeline.yaml` shape rather than a mutation of the shared file. This avoids any risk of an
in-progress v3 run accidentally picking up external-benchmark settings (or vice versa).

## Touch points (inventory — this step's whole scope)

### 1. Schema repr (0.3/7.3 pattern) — `pipeline/schema.py`

Add `build_pole_external_schema_repr() -> SchemaRepr` alongside the untouched v2/v3 builders.
Built from the 9.1 audit (`docs/neo4jpole.md`) — the **real** schema, not a designed one:

```python
def build_pole_external_schema_repr() -> SchemaRepr:
    return SchemaRepr(
        node_labels=[
            "Person", "Location", "Phone", "Email", "Officer", "PostCode",
            "Area", "PhoneCall", "Crime", "Object", "Vehicle",
        ],
        relationship_paths=[
            {"type": "CURRENT_ADDRESS",   "source": "Person",    "target": "Location"},
            {"type": "HAS_PHONE",         "source": "Person",    "target": "Phone"},
            {"type": "HAS_EMAIL",         "source": "Person",    "target": "Email"},
            {"type": "HAS_POSTCODE",      "source": "Location",  "target": "PostCode"},
            {"type": "POSTCODE_IN_AREA",  "source": "PostCode",  "target": "Area"},
            {"type": "LOCATION_IN_AREA",  "source": "Location",  "target": "Area"},
            {"type": "KNOWS_SN",          "source": "Person",    "target": "Person"},
            {"type": "KNOWS",             "source": "Person",    "target": "Person"},
            {"type": "CALLER",            "source": "PhoneCall", "target": "Phone"},
            {"type": "CALLED",            "source": "PhoneCall", "target": "Phone"},
            {"type": "KNOWS_PHONE",       "source": "Person",    "target": "Person"},
            {"type": "OCCURRED_AT",       "source": "Crime",     "target": "Location"},
            {"type": "INVESTIGATED_BY",   "source": "Crime",     "target": "Officer"},
            {"type": "INVOLVED_IN",       "source": "Vehicle",   "target": "Crime"},   # + Object->Crime
            {"type": "PARTY_TO",          "source": "Person",    "target": "Crime"},
            {"type": "FAMILY_REL",        "source": "Person",    "target": "Person"},
            {"type": "KNOWS_LW",          "source": "Person",    "target": "Person"},
        ],
        properties={
            "Person":    ["nhs_no", "name", "surname"],
            "Location":  ["address", "postcode", "latitude", "longitude"],
            "Phone":     ["phoneNo"],
            "Email":     ["email_address"],
            "Officer":   ["badge_no", "name", "surname", "rank"],
            "PostCode":  ["code"],
            "Area":      ["areaCode"],
            "PhoneCall": ["call_date", "call_time", "call_type", "call_duration"],
            "Crime":     ["id", "date", "type", "last_outcome"],
            "Object":    ["id", "description", "type"],
            "Vehicle":   ["reg", "make", "model", "year"],
            "FAMILY_REL": ["rel_type"],   # the one relationship type carrying a property (9.1)
        },
        format="nodes_and_paths",
    )
```

`INVOLVED_IN`'s true source is `Vehicle` **or** `Object` (confirmed 9.1: 978 Vehicle→Crime, 7
Object→Crime) — `SchemaRepr.relationship_paths` only carries one `{type, source, target}` triple
per entry (matching the existing v2/v3 convention of one row per pattern), so list the dominant
Vehicle→Crime pattern and note the Object exception in the properties/docstring, mirroring how
v2's `SEEN_AT`/`REGISTERED_AT` already handle single-sourced entries. Extend
`build_schema_repr(version)` with a third branch (`"pole_external"`); extend
`adapter_suffix_for_version` too — return **`"_pole_external"`** for it (a distinct suffix, not
`""`). The API model this step actually runs carries no adapters and never reads this value, so
it's inert *for this run* — but `""` would silently collide with v2's checkpoint path
(`checkpoints/{key}/sl_adapter`) if a local fine-tuned model is ever pointed at
`dataset_version: pole_external` in the future, which is exactly the kind of overwrite/collision
this project's `adapter_suffix` mechanism exists to prevent (7.4/7.5 precedent: `_v3` was chosen
for the same reason). The function must not raise for the new key (`kind: api` never reads the suffix,
but `resolve_dataset` calls it unconditionally today).

### 2. Entity registry (3.2/7.3 pattern) — `pipeline/entity_lookup/registry.py`

Following the existing exclusion rule ("excluded: referenced by exact identifiers verbatim in
questions — no fuzzy matching needed"): `Vehicle` (reg plate), `Phone`/`Email` (exact strings),
`PostCode`/`Area` (exact codes), `Crime`/`PhoneCall`/`Object` (not named entities) are excluded.

```python
ENTITY_REGISTRY_POLE_EXTERNAL: list[dict] = [
    {"label": "Person",   "id_prop": "nhs_no",    "name_props": ["name", "surname"], "extra_props": []},
    {"label": "Officer",  "id_prop": "badge_no",  "name_props": ["name", "surname"], "extra_props": ["rank"]},
    {"label": "Location", "id_prop": None,        "name_props": ["address", "postcode"], "extra_props": []},
]
```

`Location` has no single identifier property in this schema (unlike v2/v3's `location_id`) — if
`EntityCache`/`EntityLookupResult` (3.2) assume a non-null `id_prop`, either relax that assumption
(additive, record in `decisions-log.md`) or key `Location` lookups by `address` instead; resolve
whichever is less invasive once 3.2's actual code is re-read at implementation time — this is
exactly the kind of "spec leaves something genuinely ambiguous" case `ai-workflow-rules.md` §3
says to flag rather than guess silently, so implementation should stop and check before picking.
Add `registry_for_version`'s third key (`"pole_external"`).

### 3. AD prompt (3.4/7.3 pattern) — `pipeline/ambiguity/prompts.py`

Author `AD_SYSTEM_PROMPT_POLE_EXTERNAL`: same taxonomy/output-contract structure as
`AD_SYSTEM_PROMPT_V3`, with the schema block replaced by `build_pole_external_schema_repr()`'s
real labels/relationships, and four few-shots re-grounded in **real** POLE-external data already
on hand (no invention needed):
- **SCHEMA:** the `KNOWS`-family default-vs-narrow example (e.g. "How is Benjamin Hamilton
  connected to Todd Hamilton?" — bare `KNOWS` vs `FAMILY_REL` specifically).
- **ENTITY:** the Andrea George / Anne Rice exact-duplicate-name pairs (9.1 finding).
- **INTENT:** an "aside from X" superlative-tie example (I01/I10/I11's mechanism — e.g. Inspector
  rank tie at n=44).
- **TEMPORAL:** the BL1 same-day-vs-trailing-week mechanism (T20) — explicitly note in the prompt
  comment that this is a **different temporal mechanism** than v2/v3's edge-state one (9.1 finding
  #2), so a future reader doesn't assume the two prompts teach the same thing.

### 4. Disambiguator prompt (3.5/7.3 pattern) — `pipeline/disambiguator/prompts.py`

`DIS_SYSTEM_PROMPT_POLE_EXTERNAL`, same treatment — the "How to Choose" temporal rule
(`active:true` default) does not apply here (no `active` property exists in this graph); rewrite
that rule to the actual mechanism: default to same-day unless the question asks for a window/
history explicitly.

## Producing the qualitative outputs (clarifying what already exists vs what's new)

`run_evaluation.main()` **already** calls `_persist_details` on every run (added 2026-07-27,
unconditionally) — so `results/qual_records_claude-sonnet_pole_external_local.json` is produced
automatically by the same `python -m experiments.run_evaluation config/pipeline_pole_external.yaml`
invocation that produces the tables/metrics. **Nothing new to build there.** The one manual step
still required — same as every prior v3 qualitative pass — is running the downstream report
generator, unmodified (it is benchmark-agnostic: it joins on `question_id` and reads whatever
`ambiguity_type` values are present):

```
python -m experiments.analyze_qualitative results/qual_records_claude-sonnet_pole_external_local.json
```
producing `results/qualitative_analysis_claude-sonnet_pole_external_local.md` (bucket counts,
per-type stratification, fixed/regressed case studies, both_wrong sample) — the "full run should
also output results for the qualitative analysis" requirement is satisfied by running **both**
commands as one acceptance step, not by changing any code beyond the `resolve_dataset` branch
above.

## Acceptance criteria

1. Full offline suite green; **v2/v3 regression guard:** with `dataset_version: v2` or `v3` (or
   the key absent), all prompts/schema/registry/artefact paths remain byte-identical to pre-9.3
   behaviour (test compares rendered prompts + resolved paths, mirroring 7.3's own guard).
2. `build_pole_external_schema_repr()` counts: 11 labels, the 17-relationship-path list (mirror
   of 0.3/7.3's tests); `build_schema_repr("pole_external")` and
   `adapter_suffix_for_version("pole_external")` resolve without raising.
3. With `dataset_version: pole_external`, `resolve_dataset` returns the external schema repr,
   registry, and prompts, and the resolved benchmark path is `data/benchmark-pole-external.json`
   — asserted without loading any model or touching the network.
4. **Live** (external POLE Neo4j running, `ANTHROPIC_API_KEY` exported, no GPU): a full
   `run_evaluation` pass over `config/pipeline_pole_external.yaml` completes for all three
   conditions and writes `tables_claude-sonnet_pole_external_local.md`,
   `metrics_claude-sonnet_pole_external_local.json`, and
   `qual_records_claude-sonnet_pole_external_local.json`.
5. `analyze_qualitative.py` run against that `qual_records_*.json` produces
   `qualitative_analysis_claude-sonnet_pole_external_local.md` with non-empty bucket counts and at
   least the same stratification structure as the existing v3 report (schema/entity/intent/
   temporal/unambiguous rows).
6. v2/v3 artefacts in `results/` untouched; every new artefact carries the
   `pole_external_local` tag.
