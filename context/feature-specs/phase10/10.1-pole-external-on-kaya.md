# 10.1 — External POLE Graph on Kaya

**Modules:** `kaya/90_neo4j_pole_external.slurm` (new), `kaya/92_validate_pole_external.slurm`
(new), `experiments/validate_benchmark.py` (reused unchanged — `--profile pole_external`,
built in 9.2). Possibly a one-time note in `kaya/50_neo4j_pull.sh` (the Apptainer image is
already pulled; no change expected).
**Depends on:** 9.2 done (canonical `data/benchmark-pole-external.json` +
`POLE_EXTERNAL_PROFILE` in `validate_benchmark.py`). Live Neo4j via Apptainer (workflow
rule §7). **No GPU.**
**Consumed by:** 10.4 (Mistral e2e) and 10.7 (Qwen e2e) — both need this graph reachable at
`bolt://localhost:7687` on their GPU job's node.

---

## Objective

Phase 9 loaded the real `neo4j-graph-examples/pole` graph into a **local Neo4j Desktop**,
off-cluster (9.1/9.3). That instance is not reachable from Kaya compute nodes, so the local
model runs (Mistral 10.4, Qwen 10.7) have nothing to execute against. This step stands the
**same real graph** up on Kaya via the existing Apptainer/Neo4j pattern, in its own data
volume, and re-proves it with the 9.2 gate harness so the Kaya-served graph is provably the
same substrate 9.2/9.3 validated locally.

This is infrastructure only — no benchmark, schema, or pipeline code changes. v2
(`$MYGROUP/neo4j_data`) and v3 (`$MYGROUP/neo4j_data_v3`) volumes are untouched.

## Getting the data onto Kaya

The upstream dataset ships as a **Neo4j dump**, not a `.cypher` seed (unlike v2/v3), so the
load mechanism differs from `70_neo4j_v3.slurm` (which streams a `.cypher` via `cypher-shell`).
Two acceptable provenance paths — the implementer picks whichever loads cleanly against the
Kaya image (Neo4j **5.26**, per 7.2) and records the choice + exact source in the tracker row:

1. **Upstream dump** — the `neo4j-graph-examples/pole` repo's release dump
   (`https://github.com/neo4j-graph-examples/pole`). Download on the **login node** (has
   internet), stage it under `$MYGROUP/dumps/pole-external/`, load with
   `neo4j-admin database load`.
2. **Local export** — since the graph is already live in the Phase-9 local instance,
   `neo4j-admin database dump` it locally and `scp`/rclone the dump to `$MYGROUP`. Preferable
   if the upstream dump's Neo4j version is older than 5.26 and needs a migration handshake
   (`dbms.allow_upgrade`), because the local instance already matches the working schema 9.2
   validated.

**Version-compat is a real risk to check, not assume:** a dump produced by a Neo4j version
older than the 5.26 image may require `--from-path` + a first-start store upgrade, or may not
load at all. If it doesn't load cleanly, that is a genuine blocker to flag (workflow §3), and
the local-export path (2) is the documented fallback. Record whatever happens.

## Runner — `kaya/90_neo4j_pole_external.slurm`

Mirror `kaya/70_neo4j_v3.slurm` exactly (same Apptainer flags: `--no-mount /opt`,
`--writable-tmpfs`, the four bind mounts; `neo4j console` in the background under an EXIT-trap
`cleanup`; `bolt://localhost:7687` reachable from that node only), with three differences:

- Data dir `$MYGROUP/neo4j_data_pole_external` (separate — never touches v2/v3 volumes).
- The load step is `neo4j-admin database load neo4j --from-path=<dump-dir> [--overwrite-destination]`
  run **before** `neo4j console` on a fresh volume, instead of the post-start `cypher-shell`
  stream. Set the initial password via `neo4j-admin dbms set-initial-password` on the fresh
  volume first, same as 70.
- `KEEP=1` semantics identical (reuse the existing volume, skip reload).

## Validation — `kaya/92_validate_pole_external.slurm`

Mirror `kaya/72_validate_benchmark_v3.slurm` (self-contained CPU harness runner), invoking
`experiments/validate_benchmark.py --profile pole_external` against the graph served by the
90 runner (co-locate on the same node, or `srun --jobid=<id> --overlap` per `kaya/README.md`).
This reuses 9.2's `POLE_EXTERNAL_PROFILE` (17 rel types, `expected_distribution`
20-each-plus-20-null, `min_coverage=1`) with **no code change** — it is the same harness that
went green locally in 9.2.

## Acceptance criteria

1. Dump obtained and its provenance + Neo4j version recorded in the tracker row (upstream
   release vs local export; any migration flag needed).
2. `kaya/90_neo4j_pole_external.slurm` brings the graph up on a `work`-partition node; a spot
   `MATCH (n) RETURN count(*)` returns **61,521 nodes** (the count 9.3 confirmed live) and the
   relationship count is in line with 9.1's ~105.8k — proving the same graph, not a partial
   load.
3. `kaya/92_validate_pole_external.slurm` reports **all 8 gates green** against the
   Kaya-served graph (`results/benchmark_pole_external_validation.json`, `"passed": true`),
   matching 9.2's local result.
4. The `neo4j_data_pole_external` volume is separate; `neo4j_data` (v2) and `neo4j_data_v3`
   are untouched.

## Handoff

10.4 and 10.7 point their pipeline config's `neo4j.uri` at this graph (running inside the same
GPU job, or via `srun --overlap`, per `kaya/README.md` §"Neo4j on Kaya"). The volume persists
in `$MYGROUP/neo4j_data_pole_external`, so subsequent runs use `KEEP=1` and skip the reload.
