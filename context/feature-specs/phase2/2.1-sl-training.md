# 2.1 — Schema Linker Training (+ shared SFT harness)

**Modules:** `pipeline/sft.py` (shared SFT harness), `config/models.yaml` (model registry),
`config/schema_linker_train.yaml` (shared hyperparameters), `experiments/train_schema_linker.py`
**Depends on:** 1.2 (training jsonl + `build_sl_prompt`), 0.2 (`HuggingFaceLLM` base load path)
**Consumed by:** 3.1 (loads `checkpoints/{model_key}/sl_adapter/`); 2.2/2.3 (use the trained
adapter); 2.4 (reuses `pipeline/sft.py` + `config/models.yaml`); 5.4 (resolves base + adapter
paths from the registry).

---

## Objective

Fine-tune the Schema Linker as a LoRA adapter on the 1.2 jsonl, with completion-only loss
masking. Produce `checkpoints/{model_key}/sl_adapter/` — **namespaced by base model**, so the
project is not restricted to one base. Because SL and QG training are identical except for config
and data paths, this step also builds the **reusable SFT harness** (`pipeline/sft.py`) that 2.4
reuses unchanged, plus the **model registry** (`config/models.yaml`) that 2.4 and 5.4 also read.

Training is **HuggingFace-only** (LoRA can't apply to API backends). The resulting adapter is
later loaded via `HuggingFaceLLM(model_name_or_path=<base>, peft_adapter_path="checkpoints/{model_key}/sl_adapter")`
(0.2), keeping the rest of the pipeline backend-agnostic.

---

## Multi-base support — the model registry

A single registry, `config/models.yaml`, defines every base model the project can train, keyed by
a short `model_key`. **Adding a new base later = one new entry** — no code or spec change. The
registry carries the **per-model / per-architecture** fields (base id, `target_modules`, dtype,
4-bit); the training YAML carries only the **shared hyperparameters**. Adapters are namespaced
`checkpoints/{model_key}/sl_adapter` (and `.../qg_adapter` in 2.4), so multiple bases coexist
without overwriting each other.

```yaml
# config/models.yaml — the set of trainable bases (extend freely)
mistral7b:
  base: "mistralai/Mistral-7B-v0.1"
  target_modules: ["q_proj", "v_proj"]      # Mistral/Llama attention proj names
  dtype: "bfloat16"
  load_in_4bit: true                         # QLoRA — required to fit a 7–8B base on a 16 GB GPU

llama31-8b:
  base: "meta-llama/Llama-3.1-8B"
  target_modules: ["q_proj", "v_proj"]       # Llama-family: same names as Mistral
  dtype: "bfloat16"
  load_in_4bit: true

# Example future model (different family → different target_modules):
# gemma2-9b:
#   base: "google/gemma-2-9b"
#   target_modules: ["q_proj", "k_proj", "v_proj", "o_proj"]
#   dtype: "bfloat16"
#   load_in_4bit: true
```

> `target_modules` is **architecture-specific** and therefore lives in the registry, not the
> shared YAML: `["q_proj","v_proj"]` covers the Mistral/Llama family; Gemma/Qwen/Phi differ. A new
> base brings its own `target_modules`, so cross-family models are accommodated by construction.
> `load_in_4bit: true` is the default because a 7–8B base won't fit in bf16 on a 16 GB card (e.g.
> the RTX 5080); set it `false` only on a larger GPU. Record any per-model choice in `decisions-log.md`.

## Flagged decision — `max_seq_length` (you asked to surface this)

The original pass used `max_seq_length: 512`. The 2025v1 `schema` field is heterogeneous and
**some schemas are long** (large demo DBs); the neo4j Gemma fine-tune used 1600. A 512 cap
would silently truncate long schema blocks, corrupting the supervised target (the model would
be asked to produce a pattern for a schema it can't fully see).

**Resolution (concrete, not a guess):** as the first sub-task of this step, compute the
token-length distribution of `prompt + completion` over the 1.2 train split and set
`max_seq_length` to cover ~the 99th percentile. **Default starting value: 1024** (raise toward
1536/1600 if the 99th percentile exceeds it; lower only if it's comfortably under). Record the
measured percentile and the chosen value in `decisions-log.md`. Do **not** keep 512.

## Shared SFT harness — `pipeline/sft.py`

```python
# pipeline/sft.py
"""Reusable LoRA SFT harness for the Schema Linker (2.1) and Query Generator (2.4)."""
from __future__ import annotations

import torch
from transformers import PreTrainedTokenizer


def build_model_inputs(
    prompt: str,
    completion: str,
    tokenizer: PreTrainedTokenizer,
    max_seq_length: int,
) -> dict:
    """Tokenise (prompt + completion + eos); mask prompt tokens in labels with -100.

    labels: -100 for prompt and padding tokens (ignored by CrossEntropyLoss), real token
    ids for the completion. This is the completion-only loss used by both adapters.
    """
    full_text  = prompt + completion + tokenizer.eos_token
    prompt_ids = tokenizer.encode(prompt, add_special_tokens=False)
    full_ids   = tokenizer.encode(full_text, add_special_tokens=False)[:max_seq_length]
    prompt_len = min(len(prompt_ids), max_seq_length)

    labels = ([-100] * prompt_len + full_ids[prompt_len:])[:max_seq_length]
    pad_id = tokenizer.pad_token_id or tokenizer.eos_token_id
    pad = max_seq_length - len(full_ids)
    return {
        "input_ids":      torch.tensor(full_ids + [pad_id] * pad, dtype=torch.long),
        "attention_mask": torch.tensor([1] * len(full_ids) + [0] * pad, dtype=torch.long),
        "labels":         torch.tensor(labels + [-100] * pad, dtype=torch.long),
    }


def run_sft(config: dict) -> str:
    """Run LoRA SFT from a parsed config dict; return the saved adapter path.

    Steps:
      1. Load base model + tokenizer (config['model']['base']); apply config['model']['dtype']
         and, if config['model']['load_in_4bit'], a 4-bit BitsAndBytesConfig (QLoRA). Set
         pad_token if None.
      2. Wrap with PEFT LoraConfig (r, lora_alpha, target_modules, lora_dropout, bias,
         task_type) from config['peft'] — note target_modules comes from the registry.
      3. Load train/eval jsonl (config['data']); each row {"prompt","completion"} →
         build_model_inputs(..., max_seq_length). Use a torch Dataset + default collator
         (inputs are pre-padded with masked labels).
      4. transformers.Trainer with TrainingArguments from config['training']
         (epochs, per_device_train_batch_size, gradient_accumulation_steps, learning_rate,
         lr_scheduler_type, warmup_ratio, weight_decay, bf16, logging_steps, save/eval
         strategy). Train.
      5. Save the adapter to config['training']['output_dir']; return that path.
    """
    ...
```

> `run_sft` takes a flat, already-assembled `config` dict. The per-model fields (`model.base`,
> `model.dtype`, `model.load_in_4bit`, `peft.target_modules`) are merged in by the entry point
> from `config/models.yaml`; `run_sft` itself stays model-agnostic and unchanged between 2.1/2.4.

> TRL's `SFTTrainer` is an acceptable alternative, but the manual `build_model_inputs` path is
> specified because it makes completion-only masking explicit and identical across both adapters.

## `config/schema_linker_train.yaml` (shared hyperparameters only)

Per-model fields (`base`, `target_modules`, `dtype`, `load_in_4bit`) live in `config/models.yaml`;
`output_dir` is derived from the chosen `model_key`. This YAML is base-independent.

```yaml
peft:
  method: "lora"
  r: 16
  lora_alpha: 32
  lora_dropout: 0.05
  bias: "none"
  task_type: "CAUSAL_LM"
  # target_modules: comes from config/models.yaml (per architecture)

training:
  # output_dir: derived → checkpoints/{model_key}/sl_adapter
  num_train_epochs: 3
  per_device_train_batch_size: 4
  gradient_accumulation_steps: 8         # effective batch = 32
  learning_rate: 2.0e-4
  lr_scheduler_type: "cosine"
  warmup_ratio: 0.03
  max_seq_length: 1024                   # set from the token-length sub-task above (was 512)
  weight_decay: 0.001
  bf16: true
  fp16: false
  logging_steps: 50
  save_strategy: "epoch"
  evaluation_strategy: "epoch"

data:
  train_path: "data/ozsoy_schema_linker_train.jsonl"
  eval_path:  "data/ozsoy_schema_linker_eval.jsonl"
  format: "prompt_completion"
```

Entry point `experiments/train_schema_linker.py` takes `--model_key`, loads both YAMLs, assembles
the `run_sft` config, and sets the namespaced output dir:

```python
# experiments/train_schema_linker.py  --model_key mistral7b
import argparse, yaml
from pathlib import Path
from pipeline.sft import run_sft

def main():
    ap = argparse.ArgumentParser()
    ap.add_argument("--model_key", required=True)
    ap.add_argument("--models", default="config/models.yaml")
    ap.add_argument("--train", default="config/schema_linker_train.yaml")
    args = ap.parse_args()

    registry = yaml.safe_load(Path(args.models).read_text())
    if args.model_key not in registry:
        raise SystemExit(f"Unknown model_key '{args.model_key}'. Known: {list(registry)}")
    m = registry[args.model_key]
    hp = yaml.safe_load(Path(args.train).read_text())

    config = {
        "model": {"base": m["base"], "dtype": m["dtype"],
                  "load_in_4bit": m.get("load_in_4bit", False)},
        "peft":  {**hp["peft"], "target_modules": m["target_modules"]},
        "training": {**hp["training"], "output_dir": f"checkpoints/{args.model_key}/sl_adapter"},
        "data":  hp["data"],
    }
    run_sft(config)

if __name__ == "__main__":
    main()
```

So training a second base is just: `python -m experiments.train_schema_linker --model_key llama31-8b`.

## Edge cases

- Loss masking must zero-contribute prompt + padding tokens (`-100`); verify by confirming a
  tiny example's `labels` has `-100` over the prompt span and real ids over the completion.
- If `prompt + completion` exceeds `max_seq_length`, the completion (the target) may be
  truncated — this is why the length sub-task matters. Log how many training rows are truncated;
  if non-trivial, raise `max_seq_length`.
- The intrinsic Cov@5 / EM@1 evaluation requires the diverse-beam inference built in 3.1 — it is
  **not** run here. 2.1's success is "the adapter trains and the eval-set loss is sane". The
  **reported** Cov@5 (≥85% on the **POLE benchmark** — central to the disambiguation claim, since
  the disambiguator can only pick the right interpretation if it's in the top-k) is verified after
  3.1. Separately, an **optional informal spot-check** on a sample of the held-out text2cypher test
  split — reusing `experiments/probe_utils.py` (2.2) `generate_beams` + `covered` — is a debugging
  aid to confirm the adapter learned general Text2Cypher before the POLE runs. It is not specced,
  not a `MetricBundle`, and not reported; if its numbers look wrong, debug the adapter first.

## Acceptance criteria

Now (no GPU):
1. `build_model_inputs("PROMPT", "COMPL", tok, max_seq_length=32)` returns the three tensors;
   `labels` is `-100` across the prompt span and equals the token ids across the completion;
   shapes are all `[32]`.
2. `run_sft` is importable and its config-key contract is documented.
3. The entry point assembles a valid `run_sft` config from `config/models.yaml` + the train YAML:
   `--model_key mistral7b` yields `model.base`, `peft.target_modules` (from the registry), and
   `training.output_dir == "checkpoints/mistral7b/sl_adapter"`; an unknown `--model_key` exits with
   the list of known keys.

Deferred (GPU run):
4. Training completes 3 epochs; eval loss decreases; `checkpoints/{model_key}/sl_adapter/` contains
   the LoRA adapter weights + config. Training a second `--model_key` writes a sibling dir without
   touching the first.
5. The token-length sub-task is recorded and `max_seq_length` set accordingly.

---

## Handoff

`checkpoints/{model_key}/sl_adapter/` is the adapter 3.1 loads for diverse-beam inference and that
2.2/2.3 probe (for whichever `model_key` is active). `pipeline/sft.py` (`build_model_inputs`,
`run_sft`) and `config/models.yaml` are reused by 2.4. 5.4 resolves base + adapter paths from the
registry via `active_model`. Next: 2.2 sweeps `diversity_penalty` on the active adapter to lock the
inference value.
