# 7.1 — KG v3 Schema & Benchmark Co-Design

**Artefacts owned:** `data/SyntheticPoliceKG-v3.cypher`, `data/benchmark-v3-skeleton.json`
**Depends on:** nothing in code (design step). Motivated by the 5.4 end-to-end finding
(job 957276) and the 3.1 root-cause diagnosis (SL Cov@5 = 0.208 — see
`docs/results-walkthrough.md` and decisions-log 2026-06-15/3.1).
**Consumed by:** 7.2 (final benchmark + validation), 7.3 (schema module integration),
7.4 (in-domain SFT data enumerates this schema).

---

## Objective

Design the **v3 dataset substrate**: a deliberately concise POLE schema whose remaining
complexity is *designed ambiguity* (the thesis subject) rather than lexical noise, plus
the 120-question benchmark **skeleton** (questions + intended interpretations in prose,
no Cypher yet). Schema and benchmark are co-designed in this one step so the KG data can
be *seeded to support the planned questions* — every planned interpretation must have
non-empty, distinguishable result support in the data. 7.2 authors the gold Cypher and
proves that support executably.

**Why v2 is being replaced (record of intent):** v2's 28 relationship types include
accidental near-synonyms (`RELATES_TO`/`RELATED_TO`/`LINKED_TO`; seven `*_AT` location
edges; `PARTICIPATED_IN`/`INVOLVED_IN`) that deflate SL coverage without testing
disambiguation, and the v2 benchmark's uniform 1–5 hop stratification spends 40% of its
difficulty budget on long-path compositionality — orthogonal to the research question.
v2 stays frozen as the recorded baseline (job 957276).

## v3 node labels (6)

| Label | Properties | Notes |
|---|---|---|
| `Person` | `person_id`, `name`, `alias`, `date_of_birth`, `gender` | **No `role` property** — roles are expressed only by the four role edges, so there is exactly one query path per role question. |
| `Incident` | `incident_id`, `crime_type`, `date`, `status` | |
| `Case` | `case_id`, `case_name`, `status`, `opened_date` | |
| `Location` | `location_id`, `address`, `suburb`, `postcode` | |
| `Vehicle` | `vehicle_id`, `plate`, `make`, `model`, `colour` | |
| `Phone` | `device_id`, `phone_number` | |

**Dropped from v2:** `Evidence`, `Organisation`, `Communication` (and all their edges).
Nothing in the four ambiguity types requires them; `CALLED` moves cleanly to
Phone→Phone (it already is in v2).

## v3 relationship types (11)

| # | Pattern | Edge properties | Ambiguity affordance |
|---|---|---|---|
| 1 | `(Person)-[:SUSPECTED_OF]->(Incident)` | — | schema (role) |
| 2 | `(Person)-[:WITNESSED]->(Incident)` | — | schema (role) |
| 3 | `(Person)-[:VICTIM_OF]->(Incident)` | — | schema (role) |
| 4 | `(Person)-[:INVESTIGATES]->(Incident)` | — | schema (role) |
| 5 | `(Case)-[:CONTAINS]->(Incident)` | — | — |
| 6 | `(Incident)-[:OCCURRED_AT]->(Location)` | — | — |
| 7 | `(Person)-[:LIVES_AT]->(Location)` | `from_date`, `to_date`, `active` | temporal |
| 8 | `(Person)-[:OWNS]->(Vehicle)` | `from_date`, `to_date`, `active` | temporal |
| 9 | `(Person)-[:USES_PHONE]->(Phone)` | `from_date`, `to_date`, `active` | temporal |
| 10 | `(Phone)-[:CALLED]->(Phone)` | `timestamp` | — |
| 11 | `(Person)-[:ASSOCIATED_WITH]-(Person)` | `from_date`, `to_date`, `active` | temporal / schema |

**Dropped from v2 (17):** `WORKS_FOR`, `RELATES_TO`, `RELATED_TO`, `LINKED_TO`, `KNOWS`,
`PARTICIPATED_IN`, `INVOLVED_IN`, `SEEN_AT`, `LOCATED_AT`, `TOOK_PLACE_AT`,
`COLLECTED_AT`, `REGISTERED_AT`, `COLLECTED`, `HAS_EVIDENCE`, `ASSIGNED_TO`, `USED_IN`,
`MESSAGED`. Rule applied: a relationship survives only if it is *semantically* distinct
from every other survivor; vague-connector questions ("connected to", "involved with")
get their ambiguity from the **role edges (1–4)**, not from redundant generic edges.

## Data volumes & seeding requirements

Target volumes: **40 Persons, 12 Incidents, 4 Cases, 16 Locations, 10 Vehicles,
14 Phones** (constraints + indexes as in v2, adjusted to the v3 labels).

Seeding is requirement-driven, not decorative — the file must contain:

- **Entity-ambiguity seeds:** ≥4 duplicate-surname clusters (e.g. two unrelated
  "Chen"s), ≥2 shared given names, ≥2 alias collisions (one person's `alias` equals
  another's given name), ≥1 location collision (same street name in two suburbs).
- **Temporal seeds:** every Person has ≥1 `LIVES_AT`; ≥8 Persons have ≥2 dated
  `LIVES_AT` rows (moved house); ≥4 Vehicles with an ownership transfer (old
  `active:false` + new `active:true` `OWNS`); ≥4 Phones reassigned between persons.
- **Schema-ambiguity seeds:** for every incident referenced by a planned
  "connected/involved" question, the suspect, witness, and investigator sets must be
  non-empty and pairwise different (so the interpretations return different rows).
- **Cross-role persons** (suspect in one incident, witness in another) as in v2.
- Realistic Perth-metro geography retained.

## Benchmark skeleton — `data/benchmark-v3-skeleton.json`

120 entries, IDs `Q-V3-001`…`Q-V3-120`. Distribution: **40 unambiguous (`null`) +
20 schema + 20 entity + 20 intent + 20 temporal**. `num_hops` ≤ 3 for every gold
interpretation (aim roughly 45/50/25 across 1/2/3 hops — a soft target recorded as
metadata, NOT a stratification constraint; the dissertation reports single- vs
multi-hop only).

Each entry (no Cypher at this step — that is 7.2's job):

```json
{
  "question_id": "Q-V3-041",
  "question": "Show people connected to the Northbridge robbery.",
  "num_hops": 1,
  "is_ambiguous": true,
  "ambiguity_type": "schema",
  "default_interp": "Any role edge from Person to INC-V3-001",
  "planned_interpretations": ["Only suspects", "Only witnesses", "Only investigating officers"],
  "data_support": "INC-V3-001 has 3 suspects, 2 witnesses (1 overlapping), 2 investigators"
}
```

`data_support` is the traceability note tying each question to the seeded rows that
make its interpretations non-empty and pairwise distinct. Intent-ambiguity questions
(count vs list, ties under superlatives, return-shape ambiguity) note which data
property creates the divergence.

## Acceptance criteria

1. `data/SyntheticPoliceKG-v3.cypher` loads clean into a **fresh** Neo4j on Kaya
   (separate data dir — see 7.2 for the runner): node counts per label match the
   declared volumes; `db.relationshipTypes()` returns exactly the 11 types;
   `db.labels()` exactly the 6 labels.
2. Seed inventory verified by Cypher spot-queries: the entity/temporal/schema seed
   minima above all hold on the loaded graph.
3. Skeleton counts: 120 entries; 40/20/20/20/20 by type; all `num_hops` ≤ 3; every
   ambiguous entry has 2–3 `planned_interpretations` and a non-empty `data_support`.
4. Coverage: every one of the 11 relationship types is exercised by ≥3 skeleton
   questions (default or interpretation).

## Handoff

7.2 turns the skeleton into `data/benchmark-v3.json` (authoring `cypher_default` +
per-interpretation Cypher) and proves the `data_support` claims executably. 7.3 renders
this schema as `build_pole_v3_schema_repr()`. 7.4 enumerates patterns over these 11
relationship types. Any change to the label/relationship inventory after this step is a
spec deviation → decisions-log.
