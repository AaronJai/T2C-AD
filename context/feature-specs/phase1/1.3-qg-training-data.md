# 1.3 — Query Generator Training Data

**Modules:** `pipeline/query_generator/training_data.py`, `pipeline/query_generator/prompts.py`
**Depends on:** 1.1 (`extract_schema_pattern`)
**Consumed by:** 2.4 (QG fine-tuning). The shared prompt builder is also consumed by 3.6
(inference) and 5.3 (Condition 1 zero-shot).

---

## Objective

Turn the training split of `neo4j/text2cypher-2025v1` into Query Generator SFT examples whose
target is the **full gold Cypher**, and whose prompt includes a `Committed pattern:` slot
derived from the gold Cypher via `extract_schema_pattern` (1.1). This makes QG training see
the exact pattern format it will receive at inference. Also define the **shared QG prompt
builder** (two modes: with-pattern for Conditions 2 & 3, zero-shot for Condition 1).

Output: `data/ozsoy_qg_train.jsonl`, `data/ozsoy_qg_eval.jsonl` (90:10 split).

Create empty `pipeline/query_generator/__init__.py`.

---

## Source dataset — `neo4j/text2cypher-2025v1`

Same dataset and loading as 1.2 (see that spec's "Source dataset" section for the six fields
and the heterogeneous `schema` note). Load via `load_dataset("neo4j/text2cypher-2025v1",
split="train")` — auto-downloads/caches, no manual download. QG uses `question`, `schema`,
`cypher`; the other three fields are unused.

## Shared prompt builder — `pipeline/query_generator/prompts.py`

```python
# pipeline/query_generator/prompts.py
"""Query Generator prompt. Shared by training (1.3), inference (3.6), and the C1 builder (5.3)."""
from __future__ import annotations

from typing import Optional

SYSTEM_PROMPT_WITH_PATTERN = (
    "Task: Generate a Cypher query for the given question using the provided "
    "schema and committed pattern."
)
SYSTEM_PROMPT_ZERO_SHOT = (
    "Task: Generate a Cypher query for the given question using the provided schema."
)


def build_qg_prompt(
    question: str,
    schema_block: str,
    committed_pattern: Optional[str] = None,
    error_feedback: Optional[str] = None,
) -> str:
    """With committed_pattern → Conditions 2 & 3 format. Without → Condition 1 zero-shot.

    schema_block: pre-rendered schema text (a string), mirroring build_sl_prompt.
      - training (1.3): the dataset row's raw `schema` string.
      - inference (3.6) / Condition 1 (5.3): build_pole_schema_repr().to_prompt_string(
            include_properties=False).
    The zero-shot format matches the dataset's instruction format so Condition 1 is comparable
    to the published neo4j/text2cypher checkpoint results.

    error_feedback: INFERENCE-ONLY (retry path; see the retry-feedback note below). Training
    rows NEVER set it, so prompts without it remain byte-identical to the training format.
    The orchestrator composes the string (failed query + CyVer diagnostics, 5.2).
    """
    feedback_block = (
        f"Previous attempt (rejected by the validator — do not repeat its mistakes):\n"
        f"{error_feedback}\n\n"
    ) if error_feedback else ""
    if committed_pattern:
        return (
            f"{SYSTEM_PROMPT_WITH_PATTERN}\n\n"
            f"Schema:\n{schema_block}\n\n"
            f"Committed pattern:\n{committed_pattern}\n\n"
            f"{feedback_block}"
            f"Question: {question}\n"
            f"Cypher:"
        )
    return (
        f"{SYSTEM_PROMPT_ZERO_SHOT}\n\n"
        f"Schema:\n{schema_block}\n\n"
        f"{feedback_block}"
        f"Question: {question}\n"
        f"Cypher:"
    )
```

> **Retry-feedback note (amended 2026-06-10).** Every pipeline generation call is deterministic
> (`do_sample=False`), so a retry on a byte-identical prompt reproduces the identical failure —
> without feedback, the 5.2 retry loops are no-ops. The `error_feedback` block is the chosen
> repair mechanism: it appears **only** on retry calls at inference, never in training data.
> This is an accepted, deliberate train/inference skew (the alternative — sampling with
> temperature on retries — trades determinism/reproducibility for diversity and is the
> documented fallback if feedback-prompted repair underperforms; record any switch in
> `decisions-log.md`).

> **Committed-pattern format consistency (load-bearing).** QG training derives
> `committed_pattern` from `extract_schema_pattern(gold_cypher)` (1.1). At inference (3.6) the
> committed pattern is `SchemaMapping.cypher_syntax`, produced by `_build_cypher_pattern`
> (0.1) / the Disambiguator (3.5). These must share the same syntactic style or the QG
> underperforms. Acceptance test 3 below guards this directly. If a mismatch is found, the fix
> belongs in the *producer* (0.1/3.5), not here — record in `decisions-log.md`.

> **Schema source (resolved):** `build_qg_prompt` takes a pre-rendered `schema_block` string,
> so training passes the dataset row's raw `schema` field directly and inference passes the
> POLE `to_prompt_string` output. No Ozsoy-schema→`SchemaRepr` conversion is needed — that
> earlier fallback is dropped, consistent with the heterogeneous-schema note in 1.2.

## Builder — `pipeline/query_generator/training_data.py`

```python
# pipeline/query_generator/training_data.py
"""Build Query Generator SFT data from the neo4j/text2cypher-2025v1 training split."""
from __future__ import annotations

import json
from pathlib import Path
from typing import Iterable, Optional

from datasets import load_dataset

from pipeline.schema_linker.pattern_extraction import extract_schema_pattern
from pipeline.query_generator.prompts import build_qg_prompt


def build_qg_training_instance(question: str, schema_block: str, gold_cypher: str) -> Optional[dict]:
    """One QG example, or None if pattern extraction fails (row excluded).

    Note: QG keeps node-only rows (no relationship filter) — generating Cypher for a
    node-only question is still a valid QG target. Only parse failure excludes a row.
    """
    pattern = extract_schema_pattern(gold_cypher)
    if pattern is None:
        return None
    return {
        "prompt": build_qg_prompt(question, schema_block, committed_pattern=pattern),
        "completion": gold_cypher,
    }


def build_qg_dataset(
    rows: Iterable[dict],            # 2025v1 rows: question / schema / cypher (+3 unused)

    seed: int = 13,

    """For each row call build_qg_training_instance(row["question"], row["schema"],
    row["cypher"]); drop None; deterministic shuffle (seed) then 90:10 slice; write both
    jsonl files. `rows` is typically load_dataset("neo4j/text2cypher-2025v1", split="train").
    Returns a counts report."""

```

Use the **same `seed`** as 1.2 so the train/eval partition is consistent across the two
adapters (a question in SL-eval should not appear in QG-train).

## jsonl record contract (the deliverable)

```json
{"prompt": "Task: Generate a Cypher ... committed pattern.\n\nSchema:\n...\n\nCommitted pattern:\n(p:Person)-[:LIVES_AT {active:true}]->(l:Location)\n\nQuestion: <q>\nCypher:",
 "completion": "MATCH (p:Person {name:'James Whitfield'})-[:LIVES_AT {active:true}]->(l:Location) RETURN l.address, l.suburb"}
```
2.4 masks loss on the `prompt` span (completion-only loss), identical to 2.1.

## Acceptance criteria

Now (no GPU; small fixture):
1. `build_qg_prompt(q, "<schema block>", committed_pattern="(p:Person)-[:LIVES_AT]->(l:Location)")`
   contains `Committed pattern:` and ends with `Cypher:`; without a pattern it uses the
   zero-shot system text and omits the `Committed pattern:` block.
1b. With `error_feedback=None` the output is byte-identical to the pre-amendment format (training
   data unaffected); with `error_feedback="..."` the prompt contains the
   `Previous attempt (rejected` block between the pattern (or schema) block and `Question:`.
2. `build_qg_training_instance` returns `{"prompt","completion"}` for a parseable gold Cypher,
   `None` on parse failure; `completion` equals the gold Cypher verbatim.
3. **Format-consistency test (the important one):** take a `SchemaMapping` produced by
   `CandidateMapping.top1_mapping()` (0.1) for a simple POLE pattern, feed its `cypher_syntax`
   as `committed_pattern` to `build_qg_prompt` (with the POLE `to_prompt_string` output as the
   `schema_block`), and assert it slots in without structural surprises (same
   `(var:Label)-[:TYPE]->(var:Label)` shape as an `extract_schema_pattern` output for the
   equivalent gold Cypher). This is the train↔inference format guard.

Deferred (full run): yield ~90% of the 35.9k split (only parse failures excluded).

## Handoff

`build_qg_dataset` produces the two jsonl files 2.4 trains on; `build_qg_prompt` is the prompt
contract reused by 3.6 (inference) and 5.3 (Condition 1 zero-shot). Together with 1.2, the SL
and QG training corpora share the `extract_schema_pattern` pattern format and a common
train/eval seed.
