## Objective

## Configs — and the QG-properties invariant

Both configs mirror the canonical **local** configs (`pipeline_v3_qwen.yaml`,
`pipeline_pole_external_qwen.yaml`), differing in **exactly two values**: `active_model:
qwen2.5-72b` and `results_tag: {v3_qwen72, pole_external_qwen72}`.

**`qg_include_properties: true` is mandatory on both.** This is the 10.4 job-1101275 defect
class (decisions-log 2026-08-22, and the 2026-07-17 entry that reframed properties-off as a
**defect rather than an experimental condition**): `QueryGenerator` derives `include_properties`
from `prompt_style`, so a LOCAL model on the `completion` path is shown **none** of the schema's
property names unless this key is set, while an API model on the `instruct` path gets them for
free. A stage that is given "the schema" must be given all of it — the SL already passes
`include_properties=True` unconditionally on every backend, and the QG is the only stage that
was ever shown less. It cost EX C1 2→14 / C2 13→21 / C3 16→24 on external POLE when fixed, and
it silently confounded a published Claude comparison until it was caught **after** a completed
G4 run.

10.7 defended against it with two layers. **This step adds a third, because the first two are
per-run and this defect has now been introduced twice by copying a config:**

1. **Mechanical key-set diff (G0, offline).** Each new config is diffed key-set-wise against its
   canonical local counterpart; anything other than the two intended value changes fails the
   gate. (10.7's method — keep it.)
2. **Runtime assert in both G4 runners**, before any model loads:
   `assert cfg.get("qg_include_properties") is True` **and** `assert cfg["active_model"] ==
   "qwen2.5-72b"`. (10.7's method — keep it, with the model key updated.)
3. **NEW — a permanent, parametrised regression test** (`tests/test_pipeline_configs.py`):
   *for every* `config/pipeline*.yaml` whose `active_model` resolves to a `kind: local`
   registry entry, assert `qg_include_properties is True`. API-model configs are exempt by
   construction (`prompt_style: instruct` supplies properties by default) and must be asserted
   exempt, not skipped silently. **Verified to pass today** against all four local configs
   (`pipeline_v3_qgprops`, `pipeline_v3_qwen`, `pipeline_pole_external_mistral`,
   `pipeline_pole_external_qwen`), with the two `claude-sonnet` configs exempt. This turns a
   decisions-log entry that was missed twice into an executable invariant that fails in the
   offline suite the moment anyone adds a local config without it — including configs written
   long after Phase 11.

`ad: null` / `dis: null` → base Qwen-72B runs AD/Dis, consistent with every prior local column.

## Device planning — the one real code question in this step

`experiments/build_condition3.py::_device_maps()` pins **SL→`cuda:0`, QG *and* AD→`cuda:1`**
whenever ≥2 GPUs are visible (the C3 OOM fix, decisions-log 2026-06-26). At 32B's 20.2 GiB
per 4-bit load that was 20 GiB + 40 GiB — comfortable on 93.6 GiB cards. At 72B's **~41 GiB**
(11.2 leg 1 measures it) card 1 would hold **~82 GiB of weights before any KV cache**, and C3
runs `beam_k=5` group beams. This will OOM or thrash.

Extend `_device_maps()` to return **SL→0, QG→1, AD→2 when `device_count() >= 3`**, leaving the
2-GPU and 1-GPU returns **byte-identical**; request `--gres=gpu:h100:3` for both G4 runners.
Guard it with a test asserting the 2-GPU tuple is still `({"":0}, {"":1}, {"":1})` and the
1-GPU tuple still `(None, None, None)` — the same "gate the new behaviour, freeze the old"
pattern 10.6 used for `gradient_checkpointing`. Record in decisions-log.

Consequence for scheduling: 3 + 3 GPUs exceeds the node, so **the two G4 runs go sequentially**,
unlike 10.7's side-by-side pair. At 10.7's measured 1h22m (120×3) and 1h28m (100×3) for the 32B,
budget ~3 h each and keep the 24 h walltime. Both runs still need the per-job Bolt port +
isolated Neo4j data dir (`kaya/109`/`110` pattern) even when run alone — do not drop it.
