## Objective

Train Qwen2.5-72B with the **byte-identical recipe 10.6 used for the 32B**, producing the same
six-adapter layout under `checkpoints/qwen2.5-72b/`:
`{sl,qg}_adapter` (generic Ozsoy) → `{sl,qg}_adapter_v3` + `{sl,qg}_adapter_pole_external`
(POLE continue-SFT) — the exact paths `_resolve_model_specs` builds for
`active_model: qwen2.5-72b` at each `dataset_version`.

**The scientific question this step serves.** 10.7's headline finding was that *the adapter axis
dominates the model-scale axis* for schema linking: 7B→32B moved Cov@5 +2.5 pp, while
generic→in-domain moved it +22 pp (and `schema`-type Cov@5 0.00 → ~0 → 0.95 on both models).
Phase 11 adds the third scale point that tests whether the scale axis **stays** flat at 2.2× the
parameters. A null result here is a publishable finding, not a failure — the spec must not be
written as if "bigger is better" is the expected outcome.

## The six YAMLs — identical except for their names

Each new YAML is a copy of its 10.6 counterpart with **exactly two changes**: the
`output_name`/`init_adapter_path_name` (unchanged strings — the model key namespaces the path,
not the YAML) and the header comment. Concretely, every one of these must be **identical
between the 32B and 72B files**:

`peft` block (r 16 / α 32 / dropout 0.05 / bias none / CAUSAL_LM) · `num_train_epochs`
(3 generic, 2 continue) · `learning_rate` (2.0e-4 generic, 1.0e-4 continue) ·
`lr_scheduler_type: cosine` · `warmup_ratio: 0.03` · `per_device_train_batch_size: 1` ·
`gradient_accumulation_steps: 32` · `gradient_checkpointing: true` · `max_seq_length: 3584` ·
`weight_decay: 0.001` · `bf16: false` / `fp16: true` · `save_strategy`/`evaluation_strategy:
epoch` · **every `data.train_path`/`eval_path`** (same 4k Ozsoy sample, same POLE-only splits —
NOT the `_mixed` replay files).

This is checkable, so **check it mechanically** (acceptance 1) rather than by eye.

## Stage 1 — generic Ozsoy adapters

From-scratch LoRA on `data/ozsoy_{sl,qg}_train_4k.jsonl` (the same seed=13 sample 10.6 used —
do **not** regenerate), eval on `data/ozsoy_schema_linker_eval.jsonl` (1,695 rows) / the QG
equivalent. 4,000 × 3 epochs = **12,000 micro-steps**.

## Stage 2 — POLE continue-SFT (four adapters)

`init_adapter_path_name: "{sl,qg}_adapter"` → `{sl,qg}_adapter_v3` on `data/pole_{sl,qg}_train.jsonl`
(1,800 rows, POLE-only) and → `{sl,qg}_adapter_pole_external` on `data/pole_ext_{sl,qg}_train.jsonl`
(1,980 rows). 2 epochs each: **3,600** and **3,960** micro-steps.

## Compute + scheduling

Estimates below scale 10.7's **measured** 32B rate (3.03 s/micro-step, jobs 1143214/1143215) by
parameters. **11.2 leg 2 replaces the 72B column with a measurement before any job is
submitted** — if it lands >9 s/micro-step, re-derive the table and re-check the 3-day cap.

| Stage | micro-steps | 32B measured | 72B est. @ ~6.8 s |
|---|---|---|---|
| generic SL / QG | 12,000 | ~10.1 h + ~1.5 h eval | **~23 h + ~3 h eval** |
| `_v3` continue (×2) | 3,600 | ~3.0 h | **~6.8 h** |
| `_pole_external` continue (×2) | 3,960 | ~3.3 h | **~7.5 h** |

≈ **82 GPU-hours**; every job is far inside `rrifcs`'s 3-day cap. The DAG is unchanged from
10.6: generic → its two `afterok` continues, SL and QG DAGs independent.

```bash
MODEL_KEY=qwen2.5-72b bash kaya/101_train_qwen_sl.slurm   # and 102 for the QG
```

**Use one GPU per job and run jobs in parallel** — `device_map="auto"` across several cards is
naive pipeline parallelism (one GPU computes, the rest idle), so sharding a single job wastes
the node. With the two generics side by side and the four continues side by side afterwards,
calendar time is **≈ 34 h**, and two cards stay free throughout the generic phase.

**Do not introduce DDP/`torchrun` in this step.** It would cut the generic stage to ~7 h, but
`run_sft` hardcodes `device_map="auto"` (`pipeline/sft.py:181`), which is wrong under
`torchrun` — a real contract touch, out of scope here. Recorded as a known, deliberately
unexercised option.

## Acceptance criteria

1. **Recipe parity proven mechanically, not by eye:** a test (or a scripted YAML key-by-key
   diff whose output is pasted into the tracker row) asserting each 72B YAML equals its 10.6
   32B counterpart on every key listed above, with only `output_name`/`init_adapter_path_name`
   context differing. This is the acceptance criterion the whole phase rests on.
2. Stage 1: both generic runs complete at batch 1 + GC with no OOM; `eval_loss` decreases across
   the 3 epochs; `checkpoints/qwen2.5-72b/{sl,qg}_adapter` saved.
3. Stage 2: all four continues complete via `init_adapter_path` from the generic; `eval_loss`
   decreases on each POLE eval split; `checkpoints/qwen2.5-72b/{sl,qg}_adapter_{v3,pole_external}`
   saved. **Job IDs + per-run eval_loss curves for all six runs in the tracker row.**
4. **Nothing else moved:** `checkpoints/mistral7b/*` and `checkpoints/qwen2.5-32b/*` mtimes
   predate this session (confirm and state it, as 10.3/10.6 did).
5. Quick intrinsic Cov@5 per substrate with the new `_v3`/`_pole_external` SL adapters, via
   `MODEL_KEY=qwen2.5-72b sbatch --export=ALL,SUBSTRATE=…,MODEL_KEY=qwen2.5-72b kaya/104_g1_coverage_qwen.slurm`
   — a fast read before 11.4's full G1. (No change to `kaya/104` is needed: `MODEL_KEY` is
   already a knob **and** already appears in every artefact filename, so 72B results cannot
   overwrite 10.7's 32B ones. Verify that claim on the first run.)
6. Offline suite green under `t2c` (400/5 baseline).
