# 10.6 — Qwen2.5-32B Adapter Training (v3 + external POLE)

**Modules:** `config/schema_linker_train_qwen_v3.yaml`,
`config/query_generator_train_qwen_v3.yaml`,
`config/schema_linker_train_qwen_pole_external.yaml`,
`config/query_generator_train_qwen_pole_external.yaml` (four new YAMLs), Kaya runners
`kaya/98_train_qwen_v3.slurm` + `kaya/99_train_qwen_pole_external.slurm`. No pipeline code
change — `train_schema_linker.py`/`train_query_generator.py` + `run_sft` reused verbatim with
`--model_key qwen2.5-32b`.
**Depends on:** 10.5 (locked precision/registry entry), 10.2 (external `pole_ext_*` data), 7.4
(v3 `pole_*` data already exists). **GPU** (v100-32gb, workflow §7).
**Consumed by:** 10.7 (e2e measures these adapters).

---

## Objective

Fine-tune Qwen2.5-32B for **both** substrates the user named ("our custom data" = v3;
"external pole") → `checkpoints/qwen2.5-32b/{sl,qg}_adapter_v3` and
`checkpoints/qwen2.5-32b/{sl,qg}_adapter_pole_external`, the exact paths
`_resolve_model_specs` builds for `active_model: qwen2.5-32b` at each `dataset_version`.

## Design decision — from-scratch LoRA on the mixed files (NOT continue-SFT)

7.4's v3 refresh continues from a v2 Ozsoy adapter (`init_adapter_path_name`). **Qwen has no
prior adapter to continue from.** Rather than first reproducing a Qwen v2/Ozsoy adapter
(2.1/2.4-style) and then continuing, train **from-scratch LoRA in a single stage directly on
the Ozsoy-replay-mixed files** — the mix already carries general Cypher capability + in-domain
POLE, so one stage gives both. Consequences for the YAMLs:

- **No** `model.init_adapter_path_name` (fresh `LoraConfig` from `run_sft`'s default path —
  `target_modules` therefore comes from the `config/models.yaml` `qwen2.5-32b` entry).
- `training.num_train_epochs: 3` (from-scratch, like 2.1/2.4 — not the 2-epoch continue-SFT
  schedule), `learning_rate: 2.0e-4` (the from-scratch rate, not 1e-4), `bf16: false / fp16:
  true`, `max_seq_length: 3584`, `load_in_4bit` per the 10.5 lock (**4-bit**).
- **`per_device_train_batch_size: 1`** (NOT 2) in all four Qwen YAMLs, with
  `gradient_accumulation_steps: 32` to hold the effective batch. The 10.5 fit-test OOM'd at
  batch 2 — Qwen's 152k-token vocab upcasts the lm_head logits to fp32 (~4 GiB at seq 3584 ×
  batch 2), tipping the lm_head card past 32 GB. Batch 1 + gradient checkpointing is the only
  configuration that fits 2× v100-32gb.
- Data:
  - v3 YAMLs → `data/pole_sl_train_mixed.jsonl` / `data/pole_qg_train_mixed.jsonl` (7.4 files),
    eval `data/pole_{sl,qg}_eval.jsonl`; `output_name: {sl,qg}_adapter_v3`.
  - external YAMLs → `data/pole_ext_{sl,qg}_train_mixed.jsonl` (10.2), eval
    `data/pole_ext_{sl,qg}_eval.jsonl`; `output_name: {sl,qg}_adapter_pole_external`.

Record the from-scratch-vs-continue choice in the tracker row (it is a deliberate deviation
from 7.4's continue-SFT pattern, forced by Qwen having no base adapter — decisions-log if it
turns out to change a contract, otherwise the tracker row per 7.4's precedent).

## Required `run_sft` change — gradient checkpointing (10.5 hard finding)

The 10.5 fit-test proved `run_sft` **as written (2.1) OOMs even at batch 1** without gradient
checkpointing — it sets no `gradient_checkpointing` in its `TrainingArguments` today, so every
Qwen run would die at step 0. 10.6 must add it:

- Thread a `training.gradient_checkpointing` flag (default **False**) from the train config
  into `run_sft`'s `TrainingArguments`, and when true also pass
  `gradient_checkpointing_kwargs={"use_reentrant": False}` (required with PEFT/4-bit).
  Set it **true** in all four Qwen YAMLs; leave it **absent/false** in the Mistral YAMLs so
  the v2/v3/`_pole_external` Mistral runs stay **byte-identical** (regression guard).
- This is a genuine `pipeline/sft.py` contract touch (not just config) → record it in
  `decisions-log.md` per workflow §4, and note it in this step's tracker row.

## Compute note (32B, not 7B)

Four adapters to train (sl/qg × v3/external), ~72–74h each at batch 1 (10.5) → **≈293h total**,
each adapter exceeding the 72h cap. `run_sft`'s resume-from-checkpoint + skip-if-saved (2.1)
already lets a run span chained `--dependency=afterany` jobs — the runners **must** document
that chaining (as `20_train_qg.slurm` does), it is mandatory here, not optional. Train on
**`--gres=gpu:v100-32gb:2`** (the fit-test needs both 32GB cards at train time: peak 25.3 GiB
single-GPU / 43.5 GiB total); `device_map="auto"` shards across them. The ~293h wall-clock and
the single-stage-vs-Mistral-two-stage recipe difference are **acknowledged thesis limitations**
(user decision 2026-08-22), not engineered around.

## Acceptance criteria

1. The `run_sft` gradient-checkpointing flag is added and **guarded**: a test (or a
   `git stash` A/B) confirms the Mistral SL/QG `TrainingArguments` are byte-identical when the
   flag is absent/false; full offline suite green under `t2c`.
2. All four from-scratch LoRA runs complete at **batch 1 + gradient checkpointing** with no OOM;
   `eval_loss` decreases on each eval split; job IDs + losses in the tracker row.
3. Adapters saved to `checkpoints/qwen2.5-32b/{sl,qg}_adapter_v3` and `..._pole_external`;
   mistral checkpoints untouched.
4. Quick intrinsic Cov@5 sample (~25 items) for each substrate with the new SL adapter, recorded
   in the tracker row (fast read before 10.7's full G1).

## Handoff

10.7 runs the gated e2e for Qwen on v3 and external POLE via config only.
