# 1.2 — Schema Linker Training Data

**Modules:** `pipeline/schema_linker/training_data.py`, `pipeline/schema_linker/prompts.py`
**Depends on:** 1.1 (`extract_schema_pattern`), 0.3 (`SchemaRepr` / `to_prompt_string` for
the inference-side format)
**Consumed by:** 2.1 (SL fine-tuning). The shared prompt builder is also consumed by 3.1.

---

## Objective

Turn the training split of `neo4j/text2cypher-2025v1` into Schema Linker SFT examples:
`{"prompt": <instruction+schema+question>, "completion": <schema_pattern>}` JSON-lines.
The completion is `extract_schema_pattern(gold_cypher)` (1.1). Also define the **shared SL
prompt builder** used identically at training and inference to prevent train/inference skew.

Outputs:
- `data/ozsoy_schema_linker_train.jsonl`
- `data/ozsoy_schema_linker_eval.jsonl` (90:10 split of the filtered set)

The dataset's held-out `test` split (~4.44k instances) is **not** used for training. It is not a
reported thesis metric either (the three POLE conditions carry the evaluation). It is available
only for an optional, informal post-training Cov@5/EM@1 spot-check (see 2.1) to catch a broken
adapter before the POLE runs — a one-off debugging aid, not a specced or reported result.

---

## Source dataset — `neo4j/text2cypher-2025v1`

Loaded directly via HuggingFace `datasets` (auto-downloads and caches; **no manual
download step**):

```python
from datasets import load_dataset
ds = load_dataset("neo4j/text2cypher-2025v1", split="train")   # 35.9k rows; test split = 4.44k
```

Each row has six fields:

| Field | Type | Use here |
|-------|------|----------|
| `question` | str | the NL question → prompt |
| `schema` | str | the schema block → prompt (see heterogeneity note) |
| `cypher` | str | gold Cypher → `extract_schema_pattern` → completion |
| `data_source` | str (21 values) | provenance; usable for stratified reporting, not the prompt |
| `instance_id` | str | unique id; carry through for traceability if useful |
| `database_reference_alias` | str / null | demo-DB alias; not used |

> **Heterogeneous `schema` field (important).** The `schema` string is serialised
> differently per `data_source` — a prose "Node properties: - **Label** - `prop`: TYPE …"
> style, a "Graph schema: Relevant node labels and their properties …" style, a JSON blob
> (`{"Driver": {"properties": {...}}}`), a pipe/SQL style, and others. There is **no single
> format**. Feed it to the prompt **as-is**: training across diverse schema formats teaches
> the model to extract a pattern given *any* schema block, so at inference the POLE
> `nodes_and_paths` block is just one more format it handles. Do **not** attempt to parse or
> re-render these into a uniform `SchemaRepr` — it is neither easy (5+ parsers) nor desirable.
> (This supersedes the earlier "re-render Ozsoy schema" fallback — that idea is dropped.)
>
> Note: some `schema` strings are very long (large demo DBs). This bears on `max_seq_length`
> at training time — flagged for 2.1, not handled here.

## Shared prompt builder — `pipeline/schema_linker/prompts.py`

The prompt is built by one function used by both this step and the Schema Linker inference
(3.1). It takes a **pre-rendered schema block string** so training can pass the Ozsoy
instance's schema and inference can pass the POLE schema, while the instruction and user
framing stay byte-identical.

```python
# pipeline/schema_linker/prompts.py
"""Schema Linker prompt. Shared by training (1.2) and inference (3.1) — do not fork it."""
from __future__ import annotations

SL_SYSTEM = (
    "Task: Identify the relevant schema elements for the given question.\n"
    "Use only node labels, relationship types, and properties from the provided schema.\n"
    "Output a Cypher graph pattern showing which schema elements answer the question.\n"
    "Do not write a full Cypher query. Do not include WHERE clauses or RETURN clauses.\n"
    "Do not include entity-specific property values."
)


def build_sl_prompt(question: str, schema_block: str) -> str:
    """Full SL prompt up to (but not including) the target pattern.

    schema_block: pre-rendered schema text.
      - training (1.2): the Ozsoy instance's schema string.
      - inference (3.1): build_pole_schema_repr().to_prompt_string(include_properties=True).
    """
    return (
        f"{SL_SYSTEM}\n\n"
        f"Schema:\n{schema_block}\n\n"
        f"Question: {question}\n"
        f"Schema pattern:"
    )
```

> **Note (skew):** training passes the raw heterogeneous `schema` string; inference passes
> the POLE `nodes_and_paths` block. The instruction + user framing are byte-identical; only
> the schema block content/format differs, which is inherent and — given the dataset already
> spans many schema formats — something the model is trained to tolerate. This is the
> intended design, not a compromise; the earlier "re-render into nodes_and_paths" fallback is
> dropped (see Source-dataset note).

## Builder — `pipeline/schema_linker/training_data.py`

```python
# pipeline/schema_linker/training_data.py
"""Build Schema Linker SFT data from the neo4j/text2cypher-2025v1 training split."""
from __future__ import annotations

import json
from pathlib import Path
from typing import Iterable, Optional

from datasets import load_dataset

from pipeline.schema_linker.pattern_extraction import extract_schema_pattern
from pipeline.schema_linker.prompts import build_sl_prompt


def load_ozsoy_split(split: str = "train") -> Iterable[dict]:
    """Stream the dataset rows. Auto-downloads/caches; no manual download."""
    return load_dataset("neo4j/text2cypher-2025v1", split=split)


def build_sl_training_instance(question: str, schema_block: str, gold_cypher: str) -> Optional[dict]:
    """One SL example, or None if the row is excluded (per 1.1 filtering)."""
    pattern = extract_schema_pattern(gold_cypher)
    if pattern is None:
        return None
    if not _has_relationship(pattern):          # node-only → excluded
        return None
    if not _syntax_ok(pattern):                 # CyVer SyntaxValidator on the pattern
        return None
    return {"prompt": build_sl_prompt(question, schema_block), "completion": pattern}


def build_sl_dataset(
    rows: Iterable[dict],            # 2025v1 rows: fields question / schema / cypher (+3 unused)
    out_train: str | Path,
    out_eval: str | Path,
    eval_fraction: float = 0.10,
    seed: int = 13,
) -> dict:
    """For each row call build_sl_training_instance(row["question"], row["schema"],
    row["cypher"]); drop None; deterministic shuffle (seed) then 90:10 slice; write both
    jsonl files. Returns a report dict (kept, excluded-by-reason counts)."""
    ...
```

`_has_relationship(pattern)` returns True iff the pattern contains a `-[:` token (so
typeless/variable-length traversals like `-[*3]->` are excluded — they don't exercise
relationship-type linking). `_syntax_ok(pattern)` runs CyVer's `SyntaxValidator` on the
pattern. The split is a deterministic shuffle (fixed `seed`) then slice.

> Field names are confirmed: `question`, `schema`, `cypher` (the dataset also carries
> `data_source`, `instance_id`, `database_reference_alias`, unused here).

---

## jsonl record contract (the deliverable)

Each line:
```json
{"prompt": "Task: Identify ...\n\nSchema:\nNodes: ...\nPaths:\n...\n\nQuestion: <q>\nSchema pattern:",
 "completion": "(p:Person)-[:LIVES_AT {active:true}]->(l:Location)"}
```
2.1 tokenises `prompt + completion`, masking loss on the `prompt` span (completion-only loss).

---

## Acceptance criteria

Now (no GPU; needs the dataset cached locally or a small fixture):
1. `build_sl_prompt("Where does X live?", "<schema>")` ends with `Schema pattern:` and
   contains the full `SL_SYSTEM` text and `Question:` line.
2. `build_sl_training_instance` returns a dict with keys exactly `{"prompt","completion"}` for
   a relationship-bearing gold Cypher, and `None` for a node-only or parse-failing one.
3. On a small fixture of ~20 dataset-shaped rows (mixing a couple of the different `schema`
   formats), `build_sl_dataset` writes both files, every line parses as JSON with the two-key
   contract, and the reported exclusion count matches the node-only/parse-fail fixtures.

Deferred (full run): yield on the 35.9k training split is ~85–90% (~30–32K examples).

---

## Handoff

`build_sl_dataset` produces the two jsonl files 2.1 trains on; `build_sl_prompt` is the
prompt contract 3.1 reuses verbatim. The completion format equals `extract_schema_pattern`
output (1.1) — the same format the Schema Linker emits at inference and the QG expects.
