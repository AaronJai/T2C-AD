# 3.4 — Ambiguity Detector

**Modules:** `pipeline/ambiguity/detector.py`, `pipeline/ambiguity/prompts.py`
**Depends on:** 0.1 (`AmbiguityResult`, `CandidateMapping`, `EntityLookupResult`), 0.2
(`BaseLLM`), 3.1 (`CandidateMapping`), 3.2 (`EntityLookupResult`), 3.3 (`compute_ambiguity_scores`)
**Consumed by:** 3.5 (Disambiguator reads `detected_types`); orchestrator (logs
`ad_predictions`, gates the disambiguation branch).

---

## Objective

Classify a question as ambiguous (and into which of schema/entity/intent/temporal) using the
LLM as the **primary** signal, with the entropy scores (3.3) injected as **evidence**. Few-shot
prompted, not fine-tuned — works with any `BaseLLM` backend.

`(question, candidate_mapping, entity_lookup, ad_llm) → AmbiguityResult`

> **LLM decides; entropy informs.** The entropy scores appear in the prompt as a signal. They do
> **not** gate the decision. The `threshold_schema`/`threshold_entity` fields on `AmbiguityResult`
> are recorded for analysis and serve only as the **fallback** decision rule if the LLM output
> can't be parsed (below). This matches the probe finding (LLM primary, Bayesian secondary).

---

## `prompts.py` — system prompt, serialisers, user turn

The system prompt is a fixed teaching prompt (taxonomy + curated POLE schema + 4 few-shot
examples). Keep its schema section consistent with `build_pole_schema_repr` (0.3).

```python

from __future__ import annotations

from pipeline.types import CandidateMapping, EntityLookupResult

AD_SYSTEM_PROMPT = """\
You are an ambiguity classifier for a police knowledge graph question-answering system.
Your task is to determine whether a natural-language question is ambiguous with respect to
the graph schema, and if so, identify the type of ambiguity.

A question is ambiguous if it could map to more than one structurally different Cypher query,
each returning different results. A question is NOT ambiguous if all reasonable interpretations
lead to the same query result.

The knowledge graph uses a POLE schema (Person, Object, Location, Event/Incident).
Node labels: Person, Incident, Case, Location, Vehicle, Phone, Evidence, Organisation, Communication
Key relationship types:
  (Person)-[:SUSPECTED_OF]->(Incident)
  (Person)-[:WITNESSED]->(Incident)
  (Person)-[:VICTIM_OF]->(Incident)
  (Person)-[:INVESTIGATES]->(Incident)
  (Person)-[:LIVES_AT {active, from_date, to_date}]->(Location)
  (Person)-[:OWNS {active, from_date, to_date}]->(Vehicle)
  (Person)-[:USES_PHONE {active}]->(Phone)
  (Person)-[:WORKS_FOR {active}]->(Organisation)
  (Person)-[:ASSOCIATED_WITH {active, from_date, to_date}]-(Person)
  (Incident)-[:OCCURRED_AT]->(Location)
  (Case)-[:CONTAINS]->(Incident)
  (Evidence)-[:LINKED_TO]->(Person)

## Ambiguity Types
**SCHEMA**: an NL term maps to multiple relationship types / node labels / properties.
  e.g. "connected to" → SUSPECTED_OF / WITNESSED / VICTIM_OF / INVESTIGATES.
**ENTITY**: a named entity matches more than one node and the question doesn't disambiguate.
  e.g. "incidents linked to James" with two Persons named James.
**INTENT**: the target operation is underspecified; valid readings need different RETURN clauses.
  e.g. "what is the relationship between X and Y" → the type label / its properties / all paths.
**TEMPORAL**: current vs historical state unspecified, where the schema stores both via
  active/from_date/to_date. e.g. "who owns the vehicle" → current owner vs all past owners.

1. The question. 2. The schema candidate distribution (Cypher syntax + normalised scores).
3. Entity lookup results (KG instances matching mentions). 4. A schema ambiguity score and an
entity ambiguity score (0–1) from the candidate-distribution entropy — a signal, not a decision.

Respond with a JSON object ONLY. No preamble.
{"is_ambiguous": true|false, "detected_types": [], "rationale": "..."}
detected_types ⊆ {"schema","entity","intent","temporal"}; empty if not ambiguous.

## `detector.py` — the stage

```python

from pipeline.ambiguity.bayesian_scorer import compute_ambiguity_scores

                                        _format_candidate_block, _format_entity_block)
from pipeline.llm import BaseLLM, GenerationConfig
from pipeline.types import AmbiguityResult, AmbiguityType, CandidateMapping, EntityLookupResult

_VALID_TYPES = {"schema", "entity", "intent", "temporal"}


def ambiguity_detector(
    question: str,
    candidate_mapping: CandidateMapping,
    entity_lookup: EntityLookupResult,
    ad_llm: BaseLLM,
    threshold_schema: float = 0.6,
    threshold_entity: float = 0.8,
) -> AmbiguityResult:
    schema_entropy, entity_entropy = compute_ambiguity_scores(candidate_mapping, entity_lookup)
    user = build_ad_user_turn(
        question, _format_candidate_block(candidate_mapping),
        _format_entity_block(entity_lookup), schema_entropy, entity_entropy,
    )

        [{"role": "system", "content": AD_SYSTEM_PROMPT},
         {"role": "user", "content": user}],
        GenerationConfig(max_new_tokens=256, do_sample=False),
    )
    return _parse_ad_output(
        completions[0].text, schema_entropy, entity_entropy, threshold_schema, threshold_entity,

---

## Edge cases

- **Malformed/empty LLM JSON** → deterministic entropy-threshold fallback (the only place
  thresholds gate). Never raise from the detector — always return an `AmbiguityResult`.
- **`detected_types` with invalid strings** → filtered out against `_VALID_TYPES`.
- **`is_ambiguous=false` with non-empty types** → force `detected_types=[]` for consistency.
- **Multi-type** (e.g. `["schema","temporal"]`) is allowed in the output even though benchmark
  ground truth is single-typed — Detection F1 (4.2) compares on the binary `is_ambiguous`, not
  on the type set, so this is fine.
- Backend: any `BaseLLM` works (single completion). Default base model unless 5.3 overrides to an
  API backend.

---

## Acceptance criteria

Now (no GPU; the LLM call is the only deferred part):
1. `_format_candidate_block` on the four-`Person→Incident` mapping yields the ranked
   `rel_1 candidates:` block with scores; empty mapping → "No schema candidates."
2. `_format_entity_block` on a two-"James" `EntityLookupResult` yields the matches block; empty →
   "No entity ambiguity detected."
3. `_parse_ad_output('{"is_ambiguous": true, "detected_types": ["schema"], "rationale": "x"}', …)`
   → `AmbiguityResult(is_ambiguous=True, detected_types=["schema"], …)`; fenced ```json works;
   `is_ambiguous=false` with types → types forced empty.
4. `_parse_ad_output("not json", schema_entropy=0.9, entity_entropy=0.0, t_schema=0.6, …)` →
   fallback `is_ambiguous=True, detected_types=["schema"]`.

Deferred (LLM): `ambiguity_detector` end-to-end on a few benchmark questions returns sensible
classifications; full Detection F1 is computed in 4.2.

---

## Handoff

`ambiguity_detector(...) → AmbiguityResult`. The orchestrator gates: `is_ambiguous=False` →
`candidate_mapping.top1_mapping()` (bypass); `True` → Disambiguator (3.5), passing
`detected_types`, the `CandidateMapping`, the `EntityLookupResult`, and `previously_tried`.
`_format_candidate_block` / `_format_entity_block` are imported by 3.5 (shared serialisers).
