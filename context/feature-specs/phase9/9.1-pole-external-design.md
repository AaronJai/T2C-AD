## Dataset chosen

[`neo4j-graph-examples/pole`](https://github.com/neo4j-graph-examples/pole) — real Greater
Manchester, UK street-crime data (August 2017, data.gov.uk) on a POLE (Person/Object/Location/
Event) schema. ~61.5k nodes / ~105.8k relationships. Loaded into the user's **local Neo4j
Desktop** (off-cluster — this phase does not use Kaya). Chosen over CySpider, Neo4j's own
Text2Cypher 2025v1 corpus (already the SFT training corpus — reuse would risk train/test leakage),
and CypherBench, because it is a real POLE-schema graph matching the thesis's own framing.

## Schema (full inventory — the closure target for 9.2's validation)

**11 node labels:** `Person` (369), `Location` (14904), `Phone` (328), `Email` (328), `Officer`
(1000), `PostCode` (14196), `Area` (93), `PhoneCall` (534), `Crime` (28762), `Object` (7),
`Vehicle` (1000).

**17 relationship types:** `CURRENT_ADDRESS`, `HAS_PHONE`, `HAS_EMAIL`, `HAS_POSTCODE`,
`POSTCODE_IN_AREA`, `LOCATION_IN_AREA`, `KNOWS_SN`, `KNOWS`, `CALLER`, `CALLED`, `KNOWS_PHONE`,
`OCCURRED_AT`, `INVESTIGATED_BY`, `INVOLVED_IN`, `PARTY_TO`, `FAMILY_REL`, `KNOWS_LW`.

Full per-label/per-relationship property inventory (including which relationships carry
properties — only `FAMILY_REL.rel_type`; every other relationship's property list is empty) is
in `docs/neo4jpole.md`. 9.2 must author every gold Cypher against **this** inventory — it is
structurally different from the synthetic v3 schema (`pipeline/schema.py::build_pole_v3_schema_repr`)
that the rest of this project uses; do not mix the two.

## Two structural findings that reshaped the plan vs v2/v3

1. **No role-split Person→Crime edges.** Only one generic `PARTY_TO` (55 edges total).
   `INVOLVED_IN` is Vehicle→Crime (978) / Object→Crime (7) — a **scope** axis, not a role axis.
2. **No dated/state-change relationships anywhere** — every relationship's property list is empty
   except `FAMILY_REL.rel_type`. All temporal signal lives on **node** properties instead
   (`Crime.date`, `PhoneCall.call_date`/`call_time`). Temporal ambiguity for this external set was
   therefore **redefined** (user decision) to same-day-vs-trailing-week date/time-window
   ambiguity, rather than v2/v3's edge-state (`active`/`from_date`/`to_date`) mechanism — a
   **different mechanism under the same category label**. State this explicitly in any write-up
   comparing temporal EX/EA across benchmark versions; never conflate them.

Schema ambiguity reframed onto two confirmed axes (no role-edge axis exists here): the
Person-Person `KNOWS`-family (`KNOWS`/`KNOWS_SN`/`KNOWS_PHONE`/`KNOWS_LW`/`FAMILY_REL`, confirmed
default-vs-narrow — every specific type has a parallel generic `KNOWS` edge) and crime-participant
scope (`PARTY_TO` person vs `INVOLVED_IN` vehicle/object).

## Skeleton — `scratchpad/benchmark-pole-external-skeleton-draft.json`

100 entries, IDs `Q-POLE-{E,S,I,T,U}nn`. Distribution: **20 entity / 20 schema / 20 intent / 20
temporal / 20 unambiguous control** (locked by explicit user decision, matching the
per-type-reportable-cell logic v3 uses). Same shape as 7.1's `benchmark-v3-skeleton.json`:
`question_id`, `question`, `num_hops`, `is_ambiguous`, `ambiguity_type`, `default_interp`,
`planned_interpretations`, `data_support` — no Cypher (that is 9.2's job).

Every item's `data_support` is now `CONFIRMED`, traced to a real query result — the four items
originally flagged `PARTIAL`/`NEEDS VERIFICATION` (I10, I11, I15, T20) were resolved in the
2026-08-02 follow-up (raw verification queries + fixes in `decisions-log.md`); I11 was swapped
from an area-based item to a Sergeant-rank item by explicit user decision after the area axis's
only real tie turned out to already be claimed by I03. Nothing in the 100 was invented to fill a
quota.
