# 7.2 — Benchmark v3 + Executable Validation Harness

**Modules/artefacts:** `data/benchmark-v3.json`, `experiments/validate_benchmark.py`,
`kaya/70_neo4j_v3.slurm` (v3 graph runner), `kaya/72_validate_benchmark_v3.slurm`
**Depends on:** 7.1 (schema + skeleton), 0.4 (loader), 3.7/3.8 (CyVer + executor,
reused), 4.1 (`_result_sets_equal` semantics). **Live Neo4j required** — per workflow
rule §7, run the validation for real in the implementing session.
**Consumed by:** 7.3 (config points at this file), 7.5 (gate G0).

---

## Objective

Author the final 120-item `data/benchmark-v3.json` from the 7.1 skeleton — writing
`cypher_default` and per-interpretation Cypher for every item — and ship a **validation
harness that makes the benchmark's correctness executable**. The v2 benchmark's latent
defect was that nothing ever proved its interpretations return distinct, non-empty
results on the loaded graph; v3 is not "done" until the harness passes green on Kaya.

---

## Item contract (unchanged from v2 — loader compatibility is the point)

Identical JSON shape to `benchmark-updated.json`, loadable by the 0.4
`load_benchmark` with **zero code change**: `question_id`, `question`, `num_hops`,
`is_ambiguous`, `ambiguity_type ∈ {schema, entity, intent, temporal, null}`,
`default_interp`, `cypher_default`, `interpretations: [{interp, cypher}]` (empty list
for unambiguous items). The skeleton's `planned_interpretations`/`data_support` fields
do **not** carry into the final file. No migration/remapping step exists for v3 either —
it is authored to the canonical contract.

Authoring rules:
- Every Cypher (default + interpretations) uses only v3 labels/relationship
  types/properties; ≤3 relationship hops; single-line, real whitespace (the v2
  convention the executor expects).
- Ambiguous items: 2–3 interpretations, each with its own Cypher; `cypher_default`
  is the documented default reading (for schema-role questions typically the
  any-role form, as in v2's Q-016).
- Question text unique across the file; entity mentions in ambiguous-entity
  questions must hit the 7.1 duplicate-name seeds.

## Validation harness — `experiments/validate_benchmark.py`

CLI: `python -m experiments.validate_benchmark --benchmark data/benchmark-v3.json
[--report results/benchmark_v3_validation.json]`. Connects via the same
`NEO4J_URI`/`NEO4J_USERNAME`/`NEO4J_PASSWORD` env contract as 3.2+. Version-agnostic by
design (takes a path — reusable on any benchmark authored to the contract).

Gates, all must pass:

1. **Loads:** `load_benchmark` (0.4) returns items without `ValueError`.
2. **Distribution:** 120 items; 40/20/20/20/20 by `ambiguity_type`; unique
   `question_id` and question text.
3. **Syntax:** every Cypher passes CyVer `SyntaxValidator` (live driver).
4. **Schema closure:** every label/relationship type/property referenced by every
   Cypher exists in the v3 schema (7.1 inventory).
5. **Executes non-empty:** every `cypher_default` and every interpretation Cypher
   executes via `db_executor` (3.8) with `success=True` and a **non-empty** result set.
6. **Interpretations diverge:** for every ambiguous item, interpretation result sets
   are **pairwise distinct** under 4.1's comparison semantics (value-tuple,
   column-name-insensitive) — this is the gate that makes DSR/EA measurable.
7. **Hop metadata honest:** `num_hops` equals the relationship count of
   `extract_schema_pattern(cypher_default)` (1.1), and no gold Cypher exceeds 3 hops.
8. **Coverage:** each of the 11 relationship types appears in ≥3 items' gold Cypher.

Output: a JSON report (per-gate pass/fail + per-item failures) written to
`--report`; non-zero exit on any failure. Expect to iterate
`data/SyntheticPoliceKG-v3.cypher` seeds and gold Cypher together until green —
seed adjustments during this step are normal authoring, not spec deviations (a
*schema inventory* change would be a deviation → decisions-log).

## Kaya runners

- `kaya/70_neo4j_v3.slurm`: copy of `55_neo4j.slurm` loading
  `data/SyntheticPoliceKG-v3.cypher` into a **separate data dir**
  (`$MYGROUP/neo4j_data_v3/`) so the v2 graph stays intact. Same Apptainer flags
  (`--no-mount /opt --writable-tmpfs`), same first-run behaviour (init + password +
  `cypher-shell --file` load). **One required change to the 55 pattern:** 55 skips the
  load when the data volume already exists — wrong for this step's iterate-until-green
  loop, where the seed data changes between runs. The v3 script must support a
  reload (e.g. a `RELOAD=1` env that wipes `$MYGROUP/neo4j_data_v3/` before start, or
  wipe-by-default with an opt-out), so a re-run always serves the current
  `data/SyntheticPoliceKG-v3.cypher`, never a stale first load.
- `kaya/72_validate_benchmark_v3.slurm`: CPU-only job running the harness against the
  70 job's node (or start the console in-job, as 55-pattern allows).

---

## Acceptance criteria

1. Offline (no DB): harness unit tests — gate 2 catches a wrong distribution, gate 7
   catches a mislabeled `num_hops`, on small fixtures.
2. **On Kaya (live v3 graph): the full harness passes all 8 gates green** over the real
   `data/benchmark-v3.json`; the report artefact is committed to
   `results/benchmark_v3_validation.json`.
3. `load_benchmark("data/benchmark-v3.json")` + `ambiguous_items` + `items_by_type`
   return the expected 120 / 80 / {20,20,20,20} splits.

## Handoff

`data/benchmark-v3.json` is the v3 canonical benchmark **once criterion 2 passes**
(see `ai-workflow-rules.md` §6). 7.3 points `config/pipeline.yaml` at it; 7.4 uses its
question texts as the disjointness blocklist; 7.5 gate G0 is this harness re-run.
