# 10.2 — External-POLE In-Domain SFT Data

**Modules:** `pipeline/pole_sft_data.py` (additive — external-schema enumeration +
templates), `config/pole_sft_data_pole_external.yaml` (new), `experiments/build_pole_sft_data.py`
(reused; `--config` selects the external config), data outputs under `data/pole_ext_*`.
**Depends on:** 9.2 (`data/benchmark-pole-external.json` blocklist), 9.3
(`build_pole_external_schema_repr`), 7.4 (the generation machinery — reused as the template,
not rewritten), 1.1/1.2/1.3 (`extract_schema_pattern`, `build_sl_prompt`, `build_qg_prompt`
reused verbatim). API key optional (paraphrase leg). **No GPU.**
**Consumed by:** 10.3 (Mistral training) and 10.6 (Qwen training).

---

## Objective

Generate in-domain SFT examples over the **real external POLE schema** (11 labels / 17
relationship types, `build_pole_external_schema_repr()`), so a local model can be fine-tuned
for it exactly the way 7.4 produced the v3 in-domain data. Both `checkpoints/mistral7b/...`
and `checkpoints/qwen2.5-32b/...` will train on these files. Without this, the only external
adapters possible would be schema-mismatched v3 adapters — useless.

## What differs from 7.4 (do not blindly copy the v3 generator)

The external schema is structurally unlike v3, and the SFT data must reflect that:

1. **No edge-state temporal.** v3 encodes temporal ambiguity as `{active:true}` edge filters;
   this graph has **no dated/state-change relationships** (9.1 finding #2 — every rel property
   list is empty except `FAMILY_REL.rel_type`). Temporal ambiguity here is a **WHERE-clause
   value choice** on node properties (`Crime.date`, `PhoneCall.call_date/call_time`) —
   same-day-vs-trailing-week and most-recent-vs-full-history (9.1/9.4). So:
   - The **SL** target for temporal items is just the plain schema pattern (no `{active:true}`
     variant to enumerate) — the temporal decision is not a schema-element choice.
   - The **QG** completion for temporal items must carry the correct date-window / ORDER
     BY-LIMIT Cypher idioms — reuse the exact patterns 9.4 baked into
     `_QG_FEW_SHOT_API_POLE_EXTERNAL` (`toInteger(split(...))` day-of-month window incl.
     `CALLER|CALLED` bidirectional alternation; `ORDER BY ... LIMIT 1` for scope). This is
     what teaches a *fine-tuned* QG the idiom that 9.4 gave the *instruct* QG via few-shots.
2. **Enumeration:** add `enumerate_pole_external_patterns() -> list[str]` (or generalise the
   existing walker with a schema-repr argument) — deterministic depth-≤3 walk over
   `build_pole_external_schema_repr()`, both directions, **no** active-variant step. Every
   emitted pattern must pass `parse_schema_pattern` against the external repr.
3. **Templates** grounded in **real** external seed values (real names, areas, crime types
   sampled from the live graph — available locally and, after 10.1, on Kaya). Cover the
   schema-ambiguity axes 9.2/9.3 confirmed real: the digital-comm channel split
   (`KNOWS_SN`/`KNOWS_PHONE`), Crime-participant scope (`PARTY_TO` vs `INVOLVED_IN`). Do **not**
   template the KNOWS-family broad-vs-narrow framing — 9.2 (decisions-log 2026-08-03) proved it
   structurally non-divergent in this graph.

## Disjointness gate + outputs

- **Hard disjointness gate** (reuse `apply_disjointness_gate`): drop any generated question
  matching, or rapidfuzz `token_set_ratio ≥ 0.90` against, any question in
  `data/benchmark-pole-external.json`. Report drops.
- **Outputs** (same two-key jsonl contract, `build_sl_prompt`/`build_qg_prompt` with the
  external schema block so train == inference format; `seed=13`, 90:10 split), named with a
  **`pole_ext_` prefix so they never clobber the v3 `pole_` files (7.4)**:
  - `data/pole_ext_sl_train.jsonl` + `data/pole_ext_sl_eval.jsonl`
  - `data/pole_ext_qg_train.jsonl` + `data/pole_ext_qg_eval.jsonl`
  - `data/pole_ext_sl_train_mixed.jsonl` + `data/pole_ext_qg_train_mixed.jsonl` (Ozsoy replay
    mix for continue-SFT, `ozsoy_replay` knob in the new config) — target ~1,500–2,500 kept
    POLE rows before the mix.
- `config/pole_sft_data_pole_external.yaml`: same shape as `config/pole_sft_data.yaml`
  (paraphrase-LLM `build_llm` spec — **never hardcode a model**; generation knobs;
  `ozsoy_replay`), pointed at the external schema + `data/benchmark-pole-external.json`.

The additive helpers should not change any existing `pole_sft_data.py` behaviour for v3 —
guard with a schema-repr / registry argument and keep the v3 path byte-identical (mirror how
7.3 made `build_schema_repr` version-selectable).

## Acceptance criteria

1. Offline: `enumerate_pole_external_patterns` emits only in-schema patterns (every one passes
   `parse_schema_pattern` against the external repr; **no** `{active:true}` variants present —
   the external-schema asymmetry); the two-key contract holds; `extract_schema_pattern(qg) ==
   sl` for every generated row (the 1.3/7.4 train-format guard); the disjointness gate provably
   drops a planted near-duplicate of a benchmark question. New tests in
   `tests/test_pole_sft_data.py`; full suite green under `t2c`.
2. Generation run: all six jsonl files written + a report; every one of the 17 relationship
   types covered by ≥30 SL rows (or the coverage gap named explicitly, mirroring 9.2's own
   thin-coverage note for `HAS_PHONE`/`HAS_EMAIL`/`POSTCODE_IN_AREA`); temporal QG completions
   carry the 9.4 date-window/ORDER BY idioms; disjointness drops logged. (Paraphrase leg may be
   deferred if no API key, exactly as 7.4 did — template-only rows are usable.)
3. v3 `data/pole_*` files and the v3 `pole_sft_data.py` path are byte-identical (regression
   guard).

## Handoff

10.3 continue-SFTs Mistral on `data/pole_ext_{sl,qg}_train_mixed.jsonl`; 10.6 trains Qwen on
the same files. The new config documents how to regenerate for any other `model_key`.
