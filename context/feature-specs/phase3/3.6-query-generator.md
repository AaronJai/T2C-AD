# 3.6 — Query Generator Inference

**Module:** `pipeline/query_generator/generator.py`
**Depends on:** 0.1 (`SchemaMapping`, `SchemaRepr`), 0.2 (`BaseLLM`, `GenerationConfig`), 1.3
(`build_qg_prompt`), 2.4 (`checkpoints/qg_adapter/` for C2/C3)
**Consumed by:** 3.7 (validates the generated Cypher); orchestrator.

---

## Objective

Generate a Cypher query string from the original question + the committed pattern + the schema.
Greedy decoding (no beam search needed — this is generation, not distribution). Reuses
`build_qg_prompt` (1.3) so the inference prompt matches training exactly.

`(question, schema_mapping, schema) → cypher: str`

The committed-pattern vs zero-shot branch is driven by `SchemaMapping.cypher_syntax`:
- `cypher_syntax != ""` → committed-pattern prompt (Conditions 2 & 3).
- `cypher_syntax == ""` → zero-shot prompt (Condition 1). The orchestrator (5.2) supplies a
  `SchemaMapping(question, committed={}, cypher_syntax="", resolution_mode="automated")` for C1.

from __future__ import annotations

from pipeline.llm import BaseLLM, GenerationConfig
from pipeline.query_generator.prompts import build_qg_prompt
from pipeline.types import SchemaMapping, SchemaRepr


class QueryGenerator:
    def __init__(self, llm: BaseLLM):
        self.llm = llm
        self._config = GenerationConfig(
            max_new_tokens=256,   # a full Cypher query is longer than a schema pattern
            num_beams=1,          # greedy
            do_sample=False,
        )

    def generate(self, question: str, schema_mapping: SchemaMapping, schema: SchemaRepr) -> str:
        committed = schema_mapping.cypher_syntax or None    # "" → zero-shot (C1)
        prompt = build_qg_prompt(
            question,
            schema.to_prompt_string(include_properties=False),
            committed_pattern=committed,
        )
        completion = self.llm.generate(prompt, self._config)[0].text

## Edge cases

- **C1 zero-shot** uses the same `build_qg_prompt` with no committed pattern, matching the
  dataset's instruction format so C1 is comparable to the published neo4j/text2cypher checkpoint.
- **Output cleanup** matters most for C1 (base model may wrap in ``` or add prose). For C2/C3 the
  adapter is trained to emit just the query; `_clean_cypher` is still applied for safety.
- **Backend:** C2/C3 use `HuggingFaceLLM` with `qg_adapter`; C1 uses the base model. API backends
  also work (greedy, single completion). No beam scores needed here, so `AnthropicLLM` is fine for
  the QG (unlike the Schema Linker).
- The QG may receive committed patterns the adapter didn't see verbatim (e.g. untyped `-[r]->`
  from the disambiguator's "return all roles" reading) — it relies on the schema block + its
  training to generalise. This is the consideration flagged in 3.5.

## Acceptance criteria

Now (no GPU; LLM call deferred):
1. With `cypher_syntax="(p:Person)-[:SUSPECTED_OF]->(i:Incident)"`, `generate` builds a prompt
   containing the `Committed pattern:` block (assert on the prompt via a fake `BaseLLM` that
   echoes the prompt).
2. With `cypher_syntax=""`, the prompt uses the zero-shot system text and omits `Committed pattern:`.
3. `_clean_cypher` strips ```` ```cypher … ``` ```` fences and trailing prose, returning the bare
   `MATCH … RETURN …` statement; passes a plain (unfenced) statement through unchanged.

Deferred (GPU + adapter): `generate` over benchmark questions. (Intrinsic QG quality on the
held-out text2cypher split is only an optional informal spot-check per 2.1 — not a reported
metric; the QG's contribution is demonstrated by C2-over-C1 on POLE.)

## Handoff

`QueryGenerator.generate(question, schema_mapping, schema) → str`. The orchestrator passes the
result to CyVer (3.7); on a syntax failure CyVer routes back here for a retry (≤2). The QG knows
nothing about validation or routing.
