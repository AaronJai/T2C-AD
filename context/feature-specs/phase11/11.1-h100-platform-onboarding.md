## Objective

Make the H100 partition a **documented, first-class runner target** and make the two Phase-10
training runners model-agnostic, so Phase 11 can be config-only where 10.6 needed new files.

This is a bookkeeping step with a real failure mode behind it. 10.7 ran every gate on `rrifcs`
(k172) via renumbered runners with `--partition=rrifcs --gres=gpu:h100:N` baked in, and the
partition move was logged (decisions-log 2026-08-28) — but **`kaya/README.md` still documents
only the `gpu`/V100 partition**. A future session following the README submits 72B training to
a 32 GB V100 and gets a step-0 OOM. Likewise `predownload.py` hardcodes `MODEL_KEY = "mistral7b"`
and `kaya/101`/`102` hardcode `--model_key qwen2.5-32b`, so 11.3 would otherwise have to edit
files it does not own (workflow §2).

## `kaya/README.md` — new section

Add a section beside the existing Kaya ops notes recording, at minimum:

- **Partition facts** (verified 2026-08-29 via `scontrol show partition rrifcs` / `show node k172`):
  one node `k172`, `gpu:h100:4` (H100 NVL, **93.6 GiB each**), 96 CPUs, 1.5 TB RAM,
  `MaxTime=3-00:00:00`, `AllowGroups=rrifcs-users` (membership is granted manually — request it),
  `ExclusiveUser=NO` / `OverSubscribe=NO` → **exclusivity is circumstantial, not guaranteed**;
  queue long jobs while the node is quiet.
- **Submit idiom:** `--partition=rrifcs --gres=gpu:h100:<N>`; every Phase-10.7/11 runner already
  carries these directives, and any `gpu`-partition script can be redirected with the same two
  flags on the `sbatch` command line without editing the file.
- **Measured throughput** (Qwen2.5-32B, 4-bit, GC on, batch 1, seq 3584): **3.03 s/micro-step**
  on one H100 vs **14.9 s** on a v100-32gb (10.5 fit-test) — **4.9×**. Cite jobs 1143214/1143215.
- **Precision rule:** sm90 has native bf16, but **keep `dtype: float16`** as `config/models.yaml`
  sets it. Every adapter in the project shares one recipe, and switching precision on the H100
  branch alone would confound the model-scale comparison. A switch is a deviation → decisions-log.
- **Sizing rule:** one card holds one 4-bit training job (32B peaks ~25 GiB, 72B ~2.2× that), so
  **training = `gpu:h100:1` per job, run jobs in parallel rather than sharding one job**.
  End-to-end runs are different — see 11.4's `_device_maps()` note.
- **Neo4j co-location:** the per-job Bolt-port + isolated-data-dir pattern (`kaya/93`, `kaya/109`)
  is mandatory whenever two GPU jobs on k172 both need a graph. Point at those files as canon.

## `kaya/predownload.py` — additive `--model_key`

`MODEL_KEY` becomes an `argparse` flag **defaulting to `"mistral7b"`**, so a bare
`python kaya/predownload.py` stays byte-identical in behaviour. The dataset + embedding-model
snapshots remain unconditional. This restores the README's stated invariant that
`predownload.py` is the **only** login-node download path (Qwen2.5-32B and -72B were both
fetched outside it; record that in the tracker row rather than pretending otherwise).

**Record the 72B provenance** in the tracker row, verified against the cache:
`Qwen/Qwen2.5-72B`, **37 safetensors shards, 136 GiB**, `architectures: ["Qwen2ForCausalLM"]`,
`transformers_version: 4.43.1` (< the pinned `transformers<4.46` — the same low-risk position
10.5 confirmed at 32B), `vocab_size: 152064` (**identical to the 32B**, so 10.5's logit-upcast
arithmetic carries over unchanged), `tie_word_embeddings: false`, 80 layers, GQA 64/8.

## `kaya/101`/`102` — `MODEL_KEY` env

Both runners currently end in `--model_key qwen2.5-32b`. Replace with
`MODEL_KEY="${MODEL_KEY:-qwen2.5-32b}"` + `--model_key "$MODEL_KEY"`, and thread `MODEL_KEY`
through the submit path's `--export` so a whole DAG inherits it. The **default is unchanged**,
so a bare `bash kaya/101_train_qwen_sl.slurm` still submits exactly the 10.6 DAG.

The train-YAML selection stays `STAGE`-driven, so 11.3 supplies its own YAML paths via a second
env knob (`TRAIN_PREFIX`, or a `MODEL_KEY`-keyed case arm — implementer's choice, record it).
`kaya/104_g1_coverage_qwen.slurm` already reads `MODEL_KEY` and already embeds it in every
artefact filename, so **no change is needed there** and Phase 11's attribution artefacts cannot
collide with 10.7's.

## Acceptance criteria

1. `kaya/README.md` carries the new section with all six bullets above; a reader who has never
   seen this conversation can submit a correct 72B training job from the README alone.
2. `python kaya/predownload.py` (no args) is behaviourally unchanged; `--model_key qwen2.5-72b`
   re-verifies the existing cache without re-downloading (37/37 shards present).
3. `MODEL_KEY` defaulting proven: submitting `kaya/101`/`102` with no env var yields the same
   `python -m experiments.train_schema_linker --model_key qwen2.5-32b …` command line as today
   (echo/dry-run evidence in the tracker row).
4. Offline suite green under `t2c` (expect the 400/5 baseline — the 5 pre-existing
   `tests/test_run_evaluation.py` failures, unchanged since 10.6).
5. Decisions-log row recording that `rrifcs` is now the documented default GPU target for
   Phase 11, and that fp16 is retained on sm90 for cross-model recipe parity.
