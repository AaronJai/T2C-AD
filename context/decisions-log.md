# Decisions Log

A lightweight record of choices made **during implementation that deviate from the
spec** — a library behaving differently than described, an interface needing an extra
parameter, a contract that had to change. Not for pre-planned design decisions (those
live in `project-overview.md` §10) and not for routine status (that's `progress-tracker.md`).

When you pick up this project weeks later and ask "why is this the way it is?", the answer
should be here.

| 2026-06-08 | 2.1/2.4 | The risk noted in the row above ("if the smoke test OOMs, halve the batch size and double `gradient_accumulation_steps`") | The predicted OOM happened for real — `10_train_sl.slurm` (job 490755) and `20_train_qg.slurm` (job 490756) both died at step 0 with `torch.OutOfMemoryError` (15.63/15.77 GiB in use, failed to allocate 784 MiB) before the smoke test (`05_smoke_sl.slurm`) was run. Applied the predicted fix verbatim in both `config/schema_linker_train.yaml` and `config/query_generator_train.yaml`: `per_device_train_batch_size: 4 → 2`, `gradient_accumulation_steps: 8 → 16` (effective batch unchanged at 32) | `_JsonlSFTDataset` pre-pads every row to `max_seq_length` (`pipeline/sft.py`), so the 3.5x jump in `max_seq_length` (1024 → 3584, logged just above) inflates per-step activation memory by roughly the same factor — 4 sequences × 3584 tokens of fp16 activations no longer fits a 16 GB V100 alongside the 7B 4-bit base + LoRA. Halving the micro-batch and doubling accumulation keeps the optimisation trajectory (effective batch, LR schedule) identical while roughly halving peak activation memory. Re-run `kaya/05_smoke_sl.slurm` to confirm headroom before resubmitting the full 24h jobs. |
