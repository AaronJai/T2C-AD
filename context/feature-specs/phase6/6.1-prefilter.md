# 6.1 — Cosine Pre-filter (optional)

**Module:** `pipeline/prefilter.py`
**Depends on:** 0.1 (`SchemaRepr`). Uses `sentence-transformers`.
**Consumed by:** 5.2 (orchestrator, lazily, only when `use_prefilter=True`).

---

## Objective

A scalability aid, **off by default**: when a schema is much larger than POLE, narrow it to the
elements most relevant to the question before the Schema Linker sees it, so the prompt stays
focused. For the POLE graph (9 labels / 28 relationships) this is unnecessary — it exists so the
architecture scales to larger graphs, and is explicitly **not a research contribution**
(project-overview §8).

`(question, full_schema, model, top_k, similarity_threshold) → SchemaRepr` (filtered)

---

## Implementation

```python
# pipeline/prefilter.py
"""Optional cosine pre-filter: narrow a large SchemaRepr to question-relevant elements."""
from __future__ import annotations

from sentence_transformers import SentenceTransformer, util

from pipeline.types import SchemaRepr


def _path_description(path: dict[str, str]) -> str:
    """Natural-language-ish description of a relationship path for embedding."""
    return f"{path['source']} {path['type']} {path['target']}"


def cosine_prefilter(
    question: str,
    full_schema: SchemaRepr,
    model: SentenceTransformer,
    top_k: int = 20,
    similarity_threshold: float = 0.30,
) -> SchemaRepr:
    """Return a filtered SchemaRepr keeping relationship paths whose embedding is cosine-similar
    to the question (≥ threshold), always retaining at least top_k by similarity. Node labels are
    those referenced by the kept paths (plus any kept standalone labels); properties are pruned to
    the kept labels. If the schema is already small (≤ top_k paths), return it unchanged.
    """
    paths = full_schema.relationship_paths
    if len(paths) <= top_k:
        return full_schema

    q_emb = model.encode(question, convert_to_tensor=True)
    descs = [_path_description(p) for p in paths]
    p_embs = model.encode(descs, convert_to_tensor=True)
    sims = util.cos_sim(q_emb, p_embs)[0]                       # [num_paths]

    ranked = sorted(range(len(paths)), key=lambda i: float(sims[i]), reverse=True)
    keep = {i for i in ranked if float(sims[i]) >= similarity_threshold}
    keep |= set(ranked[:top_k])                                # top_k floor

    kept_paths = [paths[i] for i in sorted(keep)]
    kept_labels = {p["source"] for p in kept_paths} | {p["target"] for p in kept_paths}
    # retain label order from the original schema
    node_labels = [l for l in full_schema.node_labels if l in kept_labels]
    properties = {k: v for k, v in full_schema.properties.items()
                  if k in kept_labels or any(p["type"] == k for p in kept_paths)}

    return SchemaRepr(
        node_labels=node_labels,
        relationship_paths=kept_paths,
        properties=properties,
        format=full_schema.format,
    )
```

---

## Edge cases

- **Schema already small** (≤ `top_k` paths, i.e. POLE) → returned unchanged. So enabling the
  pre-filter on POLE is a no-op, not a risk.
- **`top_k` floor** guarantees the Schema Linker never sees an over-pruned schema even if every
  similarity is below threshold.
- Properties dict retains both kept node labels and kept relationship-type keys (edge properties).
- Filtering changes which schema the SL/QG see; the orchestrator stores the result as
  `state.filtered_schema` and uses it as `working_schema` for all downstream schema-dependent stages.

---

## Acceptance criteria

Now (no GPU; a stub embedding model returning canned vectors, or a tiny real model behind
`@pytest.mark.integration`):
1. A `SchemaRepr` with ≤ `top_k` paths is returned unchanged (identity).
2. With a stub model scoring two paths high and the rest low and `top_k` small, the result keeps the
   high-scoring paths, retains the `top_k` floor, and prunes node labels/properties to the kept set.
3. The returned object is a valid `SchemaRepr` (its `to_prompt_string` works).

---

## Handoff

`cosine_prefilter(...) → SchemaRepr`. The orchestrator imports it lazily inside the
`use_prefilter` guard (5.2), so it has no effect on the default POLE experiment and the rest of the
pipeline is unaware of it.
