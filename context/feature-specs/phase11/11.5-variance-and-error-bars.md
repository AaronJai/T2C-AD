**Modules:** `experiments/bootstrap_ci.py` (new analysis CLI, no GPU) +
`tests/test_bootstrap_ci.py`; a `docs/` table or a section appended to
`docs/results-walkthrough-qwen-72b.md`. **Optional part B only:** one train YAML pair
`config/{schema_linker,query_generator}_train_qwen_v3_seed2.yaml` and a re-run of
`kaya/104_g1_coverage_qwen.slurm`.
**Depends on:** part A — nothing beyond the existing `results/qual_records_*.json` artefacts
(runnable **today**, before 11.1). Part B — 10.6 (or 11.3, to replicate at 72B).
**No GPU for part A.** Part B: `--partition=rrifcs --gres=gpu:h100:1`.
**Consumed by:** the writeup's claims about which differences are real.

---

## Objective

Every column in the project is n=1, yet the headline claims are all **differences**: criterion #1
(ambiguous EA, C3 > C2) and criterion #2 (monotonic C1 < C2 < C3). Nothing currently states how
big a difference has to be before it means something, and the tracker has been writing around
that gap in prose — 10.4: *"small-n movements on schema (C3 15→10) and temporal (C3 20→10) are
1–2 questions on n=20 cells, at noise level"*; 10.7: *"external C2 EX 37.0 < C1 40.0 — churn
(12 lost / 9 gained)"*. Both readings are almost certainly right. Neither is evidenced.

Two independent sources of chance are being conflated in that prose, and they need different
instruments:

| Source | Question it answers | Instrument | Cost |
|---|---|---|---|
| **Benchmark sampling** | Would a different set of questions have given the same answer? | paired bootstrap over question ids | **zero GPU** |
| **Training stochasticity** | Would retraining with a different seed have given the same answer? | seed replicate | ~3 h at 32B / ~7 h at 72B |

The first is the one behind nearly every caveat actually written in this project (the per-type
cells are n=20), applies **retroactively to all existing columns**, and costs nothing. It is
therefore **required**. The second is a nice-to-have and is **optional**.

---

## Part A (REQUIRED) — paired bootstrap CIs

### Method

The per-item records are already the right shape and need no new evaluation run.
`results/qual_records_<model>_<tag>.json` is a dict of three condition keys
(`baseline` / `schema_grounded` / `disambiguation_enhanced`), each a list of per-item records
carrying `question_id`, `is_correct` (EX), `matches_any_interpretation` (EA), `is_ambiguous_gold`
and `ambiguity_type`. **The question ids are identical across all three conditions**
(verified 2026-08-29 on `qual_records_qwen2.5-32b_v3_qwen.json`), which is what makes the
paired procedure valid.

For B = 10,000 iterations with a **fixed seed** (results must be reproducible):

1. Resample **question ids** with replacement, n = the number of questions (120 for v3, 100 for
   external). One id vector per iteration.
2. Read off every condition's outcome for those same ids — **paired**, i.e. resample the
   questions, not each condition independently. Both conditions saw the same benchmark, so
   pairing cancels question-difficulty variance and yields a much tighter and correct interval
   on the difference. Two independently-drawn CIs compared by eye would understate the effects.
3. Recompute, per iteration: each condition's EX and EA, and the **deltas** C2−C1, C3−C2, C3−C1.
4. Report the 2.5th / 97.5th percentiles as the 95% CI.

Report CIs on the deltas as the headline — the claims are about differences — with per-condition
CIs secondary. Do the same over the `is_ambiguous_gold` subset (criterion #1's population) and
per `ambiguity_type` (the n=20 cells the caveats are about).

### Scope

Run it over **all** existing `results/qual_records_*.json` — mistral7b v3 + external,
claude-sonnet v3 + external, qwen2.5-32b v3 + external — plus 11.4's two 72B files. Read-only:
the tool must not modify any existing artefact.

### Honest limits, to be stated wherever the numbers appear

A CI over these questions describes sampling from *this* benchmark's question distribution. It
does not make an unrepresentative benchmark representative, and it says nothing about model
stochasticity (that is part B). Overlapping per-condition CIs do **not** imply no effect when
the paired delta CI excludes zero — say which one is being quoted.

## Part B (OPTIONAL — drop without penalty)

Retrain **one** continue-SFT pair at a second seed with everything else frozen (including every
hyperparameter in 11.3's parity list and the same data files), writing `_seed2` adapter paths so
the headline adapters are untouchable, then re-run the intrinsic Cov@5 at the same locked
`diversity_penalty`. 32B is the better buy: cheaper, and it is the column with the most reported
cells.

**Two runs give a range, not a variance estimate.** It tells you whether seed noise is ~1 pp or
~8 pp — enough to judge whether a 5 pp C2→C3 gap is safe — and must not be written up as a
confidence interval or a significance test.

## Acceptance criteria

1. `experiments/bootstrap_ci.py` runs over every existing `qual_records_*.json`, with a fixed
   seed and reproducible output; unit tests cover the paired resampling (same ids used for all
   conditions within an iteration) and a known-answer case.
2. 95% CIs reported for EX and EA per condition **and for the three deltas**, overall,
   on the ambiguous subset, and per `ambiguity_type`, for every model column.
3. The 10.4 and 10.7 "at noise level" / "churn" claims are restated with the measured intervals
   or withdrawn — including whether criterion #1 and #2's margins clear zero on each substrate.
4. All existing `results/` and `docs/` artefacts byte-unchanged (the tool is read-only).
5. Part B: if run, the seed-2 eval_loss curve and Cov@5 delta are recorded; **if not run, say so
   explicitly in the tracker row** rather than leaving it ambiguous, and keep the n=1 caveat on
   training variance in the writeup.

## Handoff

Terminal step. Its output is a property of the writeup, not of the pipeline: after it, every
difference the dissertation claims is either backed by an interval or explicitly flagged as
indicative.
