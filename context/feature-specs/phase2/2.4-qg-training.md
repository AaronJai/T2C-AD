# 2.4 — Query Generator Training

**Modules:** `config/query_generator_train.yaml` (shared hyperparameters),
`experiments/train_query_generator.py`
**Depends on:** 1.3 (training jsonl + `build_qg_prompt`), 0.2 (HF base load), 2.1 (reuses
`pipeline/sft.py` — `build_model_inputs`, `run_sft` — and `config/models.yaml`)
**Consumed by:** 3.6 (loads `checkpoints/{model_key}/qg_adapter/`).

> The dependency on 2.1 is on its **code + registry** (`pipeline/sft.py`, `config/models.yaml`),
> not on the trained SL adapter. Once those exist, 2.4 can be implemented and run independently of
> (and in parallel with) SL training.

---

## Objective

Fine-tune the Query Generator as a LoRA adapter on the 1.3 jsonl, producing
`checkpoints/{model_key}/qg_adapter/` — namespaced by base model, exactly like the SL adapter
(2.1), so the QG is trained per base too. The harness, masking, registry, and `--model_key`
mechanism are **identical** to 2.1 — this step is the QG hyperparameter YAML plus a thin entry
point. The two tasks have similar complexity, so there's no empirical basis to diverge on LR/rank
without ablation; keeping them identical is deliberate.

---

## `config/query_generator_train.yaml` (shared hyperparameters only)

Per-model fields come from `config/models.yaml` (2.1); `output_dir` is derived from `model_key`.
Identical in shape to the SL hyperparameter YAML, differing only in `data` paths (and possibly
`max_seq_length` — see edge cases).

```yaml
peft:
  method: "lora"
  r: 16
  lora_alpha: 32
  lora_dropout: 0.05
  bias: "none"
  task_type: "CAUSAL_LM"
  # target_modules: from config/models.yaml (per architecture)

training:
  # output_dir: derived → checkpoints/{model_key}/qg_adapter
  num_train_epochs: 3
  per_device_train_batch_size: 4
  gradient_accumulation_steps: 8         # effective batch = 32
  learning_rate: 2.0e-4
  lr_scheduler_type: "cosine"
  warmup_ratio: 0.03
  max_seq_length: 1024                   # schema + committed_pattern + question + cypher;
                                         # re-measure on the 1.3 jsonl (QG prompts run longer)
  weight_decay: 0.001
  bf16: true
  fp16: false
  logging_steps: 50
  save_strategy: "epoch"
  evaluation_strategy: "epoch"

data:
  train_path: "data/ozsoy_qg_train.jsonl"
  eval_path:  "data/ozsoy_qg_eval.jsonl"
  format: "prompt_completion"
```

Entry point `experiments/train_query_generator.py` mirrors `train_schema_linker.py` (2.1): takes
`--model_key`, merges `config/models.yaml` + this YAML, sets
`output_dir = checkpoints/{model_key}/qg_adapter`, and calls `run_sft`.

```python
# experiments/train_query_generator.py  --model_key mistral7b
# identical to train_schema_linker.py except:
#   --train default "config/query_generator_train.yaml"
#   output_dir = f"checkpoints/{args.model_key}/qg_adapter"
```

So: `python -m experiments.train_query_generator --model_key llama31-8b` for a second base.

## Edge cases

- **QG prompts are longer than SL prompts** (they add the `Committed pattern:` block and the
  completion is a full Cypher query, not just a pattern). Re-run the 2.1 token-length sub-task on
  the 1.3 jsonl specifically; the QG `max_seq_length` may need to be larger than the SL one.
  Record the measured value in `decisions-log.md`.
- Loss masking is completion-only (the Cypher), via the shared `build_model_inputs` — identical
  to 2.1. No QG-specific masking code.
- The `QueryGenerator` inference class (greedy decode, `num_beams=1`) is **3.6**, not here. This
  step trains and saves only.

---

## Acceptance criteria

Now (no GPU):
1. `experiments/train_query_generator.py` imports `run_sft` from `pipeline.sft`; with
   `--model_key mistral7b` it assembles a config whose `training.output_dir ==
   "checkpoints/mistral7b/qg_adapter"` and whose `peft.target_modules` comes from the registry.
2. A `{"prompt","completion"}` row from `data/ozsoy_qg_eval.jsonl` (or a fixture) passes through
   `build_model_inputs` with `labels` masked over the prompt span and real ids over the Cypher.

Deferred (GPU run):
3. Training completes 3 epochs; eval loss decreases; `checkpoints/{model_key}/qg_adapter/` contains
   the LoRA adapter weights + config.
4. The QG token-length sub-task is recorded and `max_seq_length` set accordingly.

---

## Handoff

`checkpoints/{model_key}/qg_adapter/` is the adapter 3.6 loads via
`HuggingFaceLLM(base, peft_adapter_path="checkpoints/{model_key}/qg_adapter")` for greedy Cypher
generation, paired with the matching base for that `model_key`.

**Phase 2 complete after this step** — for each trained `model_key`, both adapters exist (2.1, 2.4),
the `diversity_penalty` is locked (2.2), and the entropy signal is validated (2.3). Phase 3 begins
with 3.1, which loads the active `model_key`'s `sl_adapter` and the locked penalty.
