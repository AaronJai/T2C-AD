# 7.4 — In-Domain POLE SFT Data & Adapter Refresh

**Modules:** `pipeline/pole_sft_data.py`, `config/pole_sft_data.yaml`,
`config/schema_linker_train_v3.yaml`, `config/query_generator_train_v3.yaml`,
`experiments/build_pole_sft_data.py`, Kaya train runners.
**Depends on:** 7.1/7.2 (schema + benchmark blocklist), 7.3
(`build_pole_v3_schema_repr`), 1.1/1.2/1.3 (pattern extraction + shared prompt
builders — reused verbatim), 2.1/2.4 (`pipeline/sft.py` harness — reused verbatim).
**GPU required** for the training half (workflow rule §7).
**Consumed by:** 7.5 (the refreshed adapters are what the gates measure).

---

## Objective

Close the root-cause gap. The SL/QG adapters are fine-tuned **only** on
`neo4j/text2cypher-2025v1` and are zero-shot on POLE — the diagnosed cause of
Cov@5 = 0.208 (decisions-log 2026-06-15/3.1). This step generates **in-domain SFT
examples over the v3 schema** and refreshes both adapters. A concise schema without
in-domain training moves Cov@5 some of the way; this is the lever expected to reach
criterion #5 (≥0.85).

## Data generation — `pipeline/pole_sft_data.py`

1. **`enumerate_v3_patterns() -> list[str]`** — walk `build_pole_v3_schema_repr()` and
   emit every valid 1–3-hop schema pattern (canonical `extract_schema_pattern` format,
   1.1), including the temporal `{active:true}` filter variants. With 11 relationship
   types this is a few hundred patterns; keep it deterministic and exhaustive.
2. **Question synthesis** — for each pattern, generate NL questions two ways:
   - **Templates:** hand-written per relationship type (~3–5 surface forms each),
     slot-filled with entity values sampled from the v3 seed data (names, suburbs,
     crime types) so questions look like benchmark questions.
   - **LLM paraphrase:** rewrite each templated question via an LLM built from a
     `build_llm` spec in `config/pole_sft_data.yaml` (**never hardcode a model name**
     — API backends via the existing 0.2 factory are the expected choice), ~2–4
     paraphrases per template.
3. **Disjointness gate (hard):** drop any generated question whose normalised text
   exactly matches, or scores rapidfuzz `token_set_ratio ≥ 0.90` against, **any**
   question in `data/benchmark-v3.json` (and the skeleton). Report dropped counts.
4. **Outputs** (same two-key jsonl contract as 1.2/1.3, using `build_sl_prompt` /
   `build_qg_prompt` with the v3 schema block so train == inference format):
   - `data/pole_sl_train.jsonl` + `data/pole_sl_eval.jsonl` (SL: completion =
     schema pattern) — target ~1,500–2,500 kept rows, 90:10 split, `seed=13`.
   - `data/pole_qg_train.jsonl` + `data/pole_qg_eval.jsonl` (QG: completion = full
     executable Cypher authored alongside the pattern; single-line real whitespace —
     do **not** reproduce the Ozsoy literal-`\n` artefact, decisions-log 2026-06-16).

`experiments/build_pole_sft_data.py` is the CLI (`--config config/pole_sft_data.yaml`),
writing the four files + a generation report (pattern coverage, paraphrase yield,
disjointness drops).

## Adapter refresh

**Continue-SFT from the existing adapters** (not a from-scratch retrain — QG from
scratch needs ~106h/2 chained jobs, and the Ozsoy general capability is worth keeping):

- Train data = POLE files above **mixed with an Ozsoy replay sample** (~3–5k rows
  drawn with `seed=13` from the existing 1.2/1.3 jsonl) to resist forgetting; mix
  ratio is a config value in the v3 train YAMLs.
- Reuse `pipeline/sft.py::run_sft` unchanged; new YAMLs
  (`config/schema_linker_train_v3.yaml`, `config/query_generator_train_v3.yaml`) set
  the data paths, 2–3 epochs, and **initialise from**
  `checkpoints/{model_key}/{sl,qg}_adapter`. If `run_sft` needs an
  `init_adapter_path`-style hook, that is an anticipated small addition — record it in
  the tracker row, not the decisions-log, unless a contract changes.
- Outputs: `checkpoints/{model_key}/sl_adapter_v3`, `checkpoints/{model_key}/qg_adapter_v3`
  (v2 adapters untouched). At ~2–4k mixed rows this is **hours per adapter on a V100**,
  not days — single jobs, no chaining.

## Acceptance criteria

1. Offline: `enumerate_v3_patterns` emits only in-schema patterns (every one passes
   `parse_schema_pattern` against the v3 repr; temporal variants present); jsonl rows
   honour the two-key contract; the disjointness gate provably drops a planted
   near-duplicate of a benchmark question.
2. Generation run (API key, no GPU): all four jsonl files written; report shows every
   one of the 11 relationship types covered by ≥30 SL rows; disjointness drops logged.
3. On Kaya (GPU): both continue-SFT runs complete; eval loss decreases on the POLE
   eval split; adapters saved to the `_v3` paths.
4. Quick intrinsic check (GPU, cheap): regenerate cached beams for a ~25-item v3
   benchmark sample with `sl_adapter_v3` — report the sample Cov@5 in the tracker row.
   (The full gate is 7.5 G1; this is the fast sanity read before leaving the session.)

## Handoff

7.5 measures the refreshed adapters against the gates. The v3 train YAMLs +
`pole_sft_data.yaml` document exactly how to regenerate data and adapters for any other
`model_key` in the registry.
