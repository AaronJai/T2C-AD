Reading: these are not random typos. Every invented name is a plausible, generic property a
"typical" crime-database schema would have (type, id, description, city, title) — the model is
falling back on pretraining-prior schema conventions. CORRECTION (found while scoping the fix):
this is NOT the model ignoring properties it was shown. `pipeline/query_generator/generator.py`
calls `schema.to_prompt_string(include_properties=False)` — the QG prompt has NEVER included the
property list, for either backend, since step 3.6's original design. The local fine-tuned model
still gets the real names mostly right because it was fine-tuned on POLE-specific templated data
(Phase 7.4) and memorised them into its weights; the API model was never trained on anything
POLE-specific, so showing it the schema block minus properties leaves it with no source for the
real names at all except guessing from generic world knowledge. The fix is therefore not "tell it
to adhere to a schema it was given" — it is "give the API-backend QG the properties block the
Schema Linker already gets" (`include_properties=True`, conditional on backend so the local
fine-tuned model's prompt — and its train/inference match — stays untouched).
CyVer's Properties validator catches many of these via a live EXPLAIN check and routes the
question back to the Schema Linker for a retry (this is most of what Table 3's 47.9-51.6%
structural-repair rate is recovering); not all recover within the retry budget.

Concrete paired example (Q-041, "Show people connected to the Northbridge robbery."):

  gold (benchmark-v3.json, executable-validated):
    MATCH (p:Person)-[r]->(i:Incident {incident_id:'INC-001'}) RETURN DISTINCT p.name

  claude-sonnet generated (results/api_smoke_claude-sonnet_v3.txt, G0.5):
    MATCH (p:Person)-[r]->(i:Incident {name: 'Northbridge robbery'}) RETURN p, r, i

  Two distinct problems, illustrated side by side:
    1. `i.name` does not exist (real property: incident_id) -> a genuine content error, would
       return empty, not merely a formatting difference.
    2. `RETURN p, r, i` (whole nodes) vs `RETURN DISTINCT p.name` -> even when the entity
       selection is correct, the exact-match evaluator scores this as wrong_result purely on
       shape.

Contributing factor for problem 2: pipeline/query_generator/prompts.py::build_qg_prompt is a
bare instruction + schema + question, with NO few-shot examples, on every backend (local
fine-tuned or API) -- confirmed by reading generator.py, which calls build_qg_prompt
unconditionally. The fine-tuned local model learns the exact output shape from thousands of
SFT training examples using this same prompt; the API model only ever sees this one bare
instruction, so it has no worked example to imitate the gold's projection style. By contrast,
the Schema Linker, Ambiguity Detector, and Disambiguator prompts for the API model DO carry
authored few-shot examples (pipeline/schema_linker/prompts.py::build_sl_prompt_api,
pipeline/ambiguity/prompts.py, pipeline/disambiguator/prompts.py) -- the QG is the one stage
left without any worked example, which may be the cheapest lever to try next.
