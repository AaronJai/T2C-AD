**Modules:** `pipeline/ambiguity/prompts.py` (additive), `pipeline/disambiguator/prompts.py`

## Objective

9.3's live run (decisions-log 2026-08-05, confirmed in a follow-up investigation 2026-08-06) found
temporal EA at 0/0/0 across all three conditions (C1/C2/C3) on `data/benchmark-pole-external.json`,
the only ambiguity type that stayed at zero everywhere. That session correctly declined to fix it
mid-step (9.3 was scoped to wiring + running the benchmark, not debugging a result) and recorded
it as a genuine external-validity finding. This step is the follow-up: fix what's fixable without
touching the frozen `pipeline/types.py` (0.1) contract, and get temporal EA off zero with C3
actually able to beat C2 — mirroring the entity/schema per-type gains 9.3 already achieved.

---

## Root cause (2026-08-06 investigation — full detail in decisions-log)

Three **independent, compounding** defects, not one. Fixing only one leaves items broken for a
different reason.

**The benchmark's 20 temporal items are actually three structurally different mechanisms**
(confirmed by reading every item's gold interpretations in `data/benchmark-pole-external.json`),
not the single "same-day vs trailing-week" mechanism the 9.3 prompts describe:

1. **Crime.date day-window** (10 items: T01–T04, T07, T08, T16–T19) — "crimes around date X":
   same-day vs a trailing-N-day window. Gold Cypher uses
   `toInteger(split(c.date,'/')[0]) = N` / `>= X AND <= Y` (day-of-month extraction, not string
   date-range comparison — this matters, see Defect C below).
2. **PhoneCall.call_date day-window** (3 items: T13–T15) — same mechanism as #1, on
   `PhoneCall.call_date` instead of `Crime.date`, and the gold pattern requires matching calls in
   *either* direction (`<-[:CALLER|CALLED]-`).
3. **Most-recent-contact vs full-history** (7 items: T05, T06, T09–T12, T20) — "when did phone X
   last contact phone Y": a `ORDER BY call_date DESC, call_time DESC LIMIT 1` vs no limit choice.
   This is **not a date-window choice at all** — it's a query-shape/scope choice.

**Defect A — AD never detects mechanism 3.** `AD_SYSTEM_PROMPT_POLE_EXTERNAL`'s TEMPORAL
definition and its only temporal few-shot (`_AD_FEW_SHOT_POLE_EXTERNAL` Example 4) exclusively
describe the day-window mechanism. Checked directly against the 9.3 run's
`qual_records_claude-sonnet_pole_external_local.json`: all 7 mechanism-3 items got
`ad_predicted_ambiguous: False` / `detected_types: []` in C3 — 0% recall, every one silently
routed as unambiguous and never reached the Disambiguator at all. This is upstream of Defects B
and C for these 7 items specifically: nothing downstream can fix what AD never flags.

**Defect B — the Disambiguator's committed pattern drops the resolved decision (mechanisms 1/2).**
`DIS_SYSTEM_PROMPT_POLE_EXTERNAL`'s own few-shot (`_DIS_FEW_SHOT_POLE_EXTERNAL` Example 3,
`prompts.py:299`) reasons through same-day-vs-window correctly in `rationale` but is taught to
emit a `committed_pattern` that is bare graph shape — `(c:Crime)-[:OCCURRED_AT]->(l:Location)-
[:LOCATION_IN_AREA]->(a:Area)` — with the date decision nowhere in the string the QG actually
reads. Confirmed directly: Q-POLE-T01's C2 and C3 generated Cypher are byte-identical. This is
**not** a limitation of the `SchemaMapping`/`cypher_syntax` contract itself — `cypher_syntax` is
unconstrained free text ("a prompt hint... injected into the QG prompt", `types.py:156`), and
v2/v3's own Dis few-shot already embeds a literal filter the same way for its `active:true`
mechanism (`_DIS_FEW_SHOT_V3` Example 3: `"(p:Person)-[:OWNS {active:true}]->(v:Vehicle)"`). The
mechanism exists and already works elsewhere in this codebase; the POLE-external prompt authored
in 9.3 just never used it for the date case.

**Defect C — the QG has no schema-grounded few-shot for this dataset at all.** The API-model QG
prompt (`pipeline/query_generator/prompts.py`) has never had a `pole_external` branch — unlike
every other stage (AD/Dis/schema/registry all got a proper third branch in 9.3),
`_QG_FEW_SHOT_API` is one shared block reused verbatim from the *other* synthetic-POLE dataset
(v2/v3's `Incident`/`Case`/`active:true` vocabulary), with zero version branching. Confirmed
directly across all 20 temporal items × all 3 conditions in the 9.3 run:
- 10/20 (mechanism 1) → **every condition, including the zero-shot C1 baseline**, emits an
  ISO-8601 literal (`c.date >= '2017-08-09'`) against data stored as `'09/08/2017'`
  (`DD/MM/YYYY` string). 0/20 ever produced the correct format, in any condition.
- 3/20 (mechanism 2) → same ISO-format bug, plus AD/Dis correctly detect and commit but the QG's
  generated Cypher only matches `CALLER`, never `CALLED` (misses half the real calls).
- 7/20 (mechanism 3) → when exercised via C1/C2 (bypassing Defect A), the QG hallucinates
  property names that aren't in the schema at all — `pc.callDate`, `call.datetime`, `call.start`,
  `call.startTime` — despite `PhoneCall: ["call_date", "call_time", ...]` being correctly listed
  in the properties block it's shown (`include_properties=True` on the API path). A bare property
  list is weaker grounding than a worked example; it has none for this schema.

**Why C1 (zero-shot, no schema/disambiguation at all) is also 0/20:** Defect C alone explains it —
there is no disambiguation step in C1, so Defects A/B are moot for that condition, and the QG's
format/property-name mistakes zero it regardless.

## Fix plan

### 1. AD prompt — close Defect A — `pipeline/ambiguity/prompts.py`

Extend `_AD_SYSTEM_HEAD_POLE_EXTERNAL`'s **TEMPORAL** bullet to cover both mechanisms: a
date/time *window* is unspecified (existing text) **or** the *scope* of a time-ordered relation is
unspecified (most-recent-single-result vs the full history) — both are "which of several readings
of an implicit time constraint" and both return different, non-overlapping results.

Add a 5th few-shot to `_AD_FEW_SHOT_POLE_EXTERNAL`, grounded in a real mechanism-3 item (e.g.
Q-POLE-T05's shape: "When did phone X last contact phone Y?"), showing the AD correctly flagging
`detected_types: ["temporal"]` with a rationale about most-recent vs full-history — not a
date-window rationale, so a future reader doesn't conflate the two mechanisms this prompt now
teaches.

### 2. Disambiguator prompt — close Defect B — `pipeline/disambiguator/prompts.py`

Rewrite `DIS_SYSTEM_PROMPT_POLE_EXTERNAL`'s temporal "How to Choose" rule and few-shot(s) so
`committed_pattern` carries the resolved decision, not just the schema shape, for **both**
mechanisms:

- **Day-window mechanism (1/2):** teach the Dis to embed the resolved filter using the same
  `toInteger(split(<date_prop>,'/')[0]) = N` / `>= X AND <= Y` idiom the benchmark's own gold
  Cypher already uses (confirmed above) — e.g. `committed_pattern`:
  `"(c:Crime)-[:OCCURRED_AT]->(l:Location)-[:LOCATION_IN_AREA]->(a:Area) WHERE
  toInteger(split(c.date,'/')[0]) = 11"` for same-day, or the `>=`/`<=` form for a window. This
  was chosen over having the Dis compute and embed literal `DD/MM/YYYY` date strings (which would
  need month-rollover-aware calendar arithmetic — T03's "1–4 Aug clipped at month start" case
  shows this isn't trivial) — per the user's direction, the day-extraction idiom generalizes to
  *any* window width or explicit range the question implies, not just a hardcoded same-day/
  trailing-week binary, and it's the same logic the gold queries and grading already use, so a
  correctly-reasoned Dis output is mechanically closer to gold. This is genuinely Track B "option
  1" (full resolved-value embedding), scoped to day-of-month arithmetic instead of full calendar
  dates to keep it low-risk.
- **Most-recent-vs-full-history mechanism (3):** a new few-shot where `committed_pattern` embeds
  `ORDER BY pc.call_date DESC, pc.call_time DESC LIMIT 1` for the "most recent" reading, or omits
  it for "full history" — this one is pure schema/query-shape (no computed literal at all), so it
  carries no date-arithmetic risk.

**Check at implementation time (flagging per `ai-workflow-rules.md` §3, not deciding here):**
`_pattern_to_committed`/`parse_schema_pattern` (`disambiguator.py:155`, `pattern_extraction.py`)
today assume bare `(a)-[:REL]->(b)` chains for building the *secondary* `committed` metadata dict.
A pattern with an embedded `WHERE`/`ORDER BY`/`LIMIT` clause may not parse cleanly. Per the
existing docstring ("`committed` is secondary metadata — `cypher_syntax` is authoritative for the
QG"), the likely-correct behaviour is: best-effort parse the leading relationship-chain portion for
`committed`, ignore the trailing clause for that purpose only, and pass `cypher_syntax` through
verbatim regardless — but confirm `parse_schema_pattern` doesn't raise/crash on the extended
patterns (as opposed to silently truncating) before relying on this.

### 3. QG prompt — close Defect C — `pipeline/query_generator/prompts.py`

Add a genuinely independent `pole_external` branch — not a reuse of `_QG_FEW_SHOT_API` — mirroring
the pattern already used for AD/Dis/schema/registry in 9.3. New `_QG_FEW_SHOT_API_POLE_EXTERNAL`
few-shot block, authored from the real schema, covering:
- A `Crime.date` day-window filter using the `toInteger(split(...))` idiom (so the QG's own
  from-scratch reasoning on C1/C2 — where no `committed_pattern` exists to copy from — also lands
  on the right convention, not just C3).
- A `PhoneCall` most-recent-contact query using the real `call_date`/`call_time` property names
  and the bidirectional `<-[:CALLER|CALLED]-` pattern.

Add one instruction line to the system prompt: when `committed_pattern` already contains a
`WHERE`/`ORDER BY`/`LIMIT` clause, copy it verbatim rather than re-deriving or reformatting it —
this is what makes Defect B's fix actually reach the final query instead of being second-guessed.

**Plumbing** (new, additive key — mirrors how `ad_system_prompt`/`dis_system_prompt` already flow
through `resolve_dataset`):
- `resolve_dataset` (`experiments/run_evaluation.py`) gains a `"qg_few_shot"` key: `None` for v2/v3
  (byte-identical — `QueryGenerator` keeps using its built-in `_QG_FEW_SHOT_API` default),
  `_QG_FEW_SHOT_API_POLE_EXTERNAL` for `pole_external`.
- `build_condition1`/`build_condition2`/`build_condition3` gain a `qg_few_shot: Optional[str] =
  None` passthrough param to `QueryGenerator(...)`.
- `QueryGenerator.__init__` (`pipeline/query_generator/generator.py`) gains a
  `few_shot_override: Optional[str] = None` param; when set, `build_qg_prompt_api` renders it in
  place of the module-level `_QG_FEW_SHOT_API` constant. `build_qg_prompt` (the non-API/local
  fine-tuned completion path) is untouched — the local QG was trained on v2/v3-only data and isn't
  in scope here (no `pole_external`-trained local adapter exists; the API model is what 9.3 ran).

### 4. `experiments/run_evaluation.py::resolve_dataset`

Add `"qg_few_shot"` to all three branches as described above. v2 and v3 branches get `None`
(regression guard: byte-identical resolved dict shape aside from the new key existing everywhere).

## Acceptance criteria

1. Full offline suite green; **v2/v3 regression guard** extended: with `dataset_version: v2`/`v3`
   (or absent), `resolve_dataset()["qg_few_shot"]` is `None` and the rendered QG prompt is
   byte-identical to pre-9.4 output (existing `_QG_FEW_SHOT_API` block, no new instruction line).
2. `AD_SYSTEM_PROMPT_POLE_EXTERNAL` contains 5 few-shots (was 4) and its TEMPORAL definition text
   covers both the day-window and most-recent-vs-full-history mechanisms — asserted directly on
   the module constant, mirroring the existing 4-few-shot assertion pattern in
   `tests/test_pole_external_integration.py`.
3. `DIS_SYSTEM_PROMPT_POLE_EXTERNAL`'s temporal few-shot(s), fed through a fake LLM returning each
   new example's expected `committed_pattern`, parse via `_parse_disambiguator_output` without
   raising, and the resulting `SchemaMapping.cypher_syntax` contains the embedded
   `WHERE`/`ORDER BY`/`LIMIT` text verbatim (not stripped).
4. `resolve_dataset({"dataset_version": "pole_external", ...})["qg_few_shot"]` resolves to
   `_QG_FEW_SHOT_API_POLE_EXTERNAL` without loading any model or touching the network; the v2/v3
   branches resolve to `None`.
5. **Live** (external POLE Neo4j + `ANTHROPIC_API_KEY`, no GPU): rerun `run_evaluation` against
   `config/pipeline_pole_external.yaml`, then `analyze_qualitative.py` on the resulting
   `qual_records_*.json`. Compare the new per-type temporal row against 9.3's recorded 0/0/0.
   **Success bar** (mirrors the project-overview success criteria already used for entity/schema):
   temporal EA nonzero in at least C2/C3, and C3 ≥ C2 (disambiguation actually adds value over
   schema-grounding alone, not just format-fixed-but-flat). If C3 still doesn't beat C2 after this
   fix, that itself is a smaller, more precise finding than 9.3's ("format fixed, but the
   day-window literal still isn't reaching the QG correctly") — investigate before declaring done.
6. v2/v3 artefacts in `results/` untouched; rerun artefacts overwrite the existing
   `pole_external_local`-tagged files (same tag — this is a fix to the same benchmark run, not a
   new variant) with results/decisions-log noting the before/after numbers.

## Handoff

If criterion 5's bar is cleared, Phase 9's temporal finding changes from "architecturally
unaddressable, out of scope" to "was three specific, fixed defects" — a stronger dissertation
result. If the bar is only partially cleared (e.g. mechanism 3 fixed via Defect A/QG grounding but
mechanism 1/2's embedded-literal path still doesn't survive to the final query), record the
narrowed finding and treat further iteration as optional follow-on, same posture 9.3 took.
