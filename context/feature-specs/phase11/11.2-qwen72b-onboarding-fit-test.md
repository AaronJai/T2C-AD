# 11.2 — Qwen2.5-72B Onboarding + H100 Throughput Fit-Test

**Modules:** `config/models.yaml` (new `qwen2.5-72b` entry), `kaya/qwen_fit_test.py` (additive
`--model_key`, default `qwen2.5-32b`), `kaya/111_qwen72b_fit_test.slurm` (new).
`pipeline/llm/huggingface.py` and `pipeline/sft.py` are reused **unchanged** — Qwen2.5-72B is
the same `Qwen2ForCausalLM` as the 32B on the same `transformers<4.46` pin. Any forced loader
change is a deviation → decisions-log.
**Depends on:** 11.1 (documented platform), 10.5 (the fit-test harness), 0.2, 2.1.
**GPU: `--partition=rrifcs --gres=gpu:h100:1`** (one card; see below).
**Consumed by:** 11.3 (training budget + confirmed memory), 11.4 (e2e device planning).

---

## Objective

Onboard `qwen2.5-72b` as a registry key and **measure its real throughput and memory on an
H100** before committing ~82 GPU-hours to training.

**This is a calibration, not a GO/NO-GO.** 10.5 had to decide whether a 32B model ran at all
and at what precision; none of that is open here. Same architecture family, same loader, same
tokenizer family, same 152,064-token vocabulary (so 10.5's fp32 logit-upcast arithmetic is
literally unchanged), same pinned transformers. The spec therefore **forbids re-deciding**
settled choices and asks only for numbers.

### Inherited, NOT re-decided (the parity clause)

`load_in_4bit: true` · `dtype: float16` · `target_modules: ["q_proj","v_proj"]` ·
`per_device_train_batch_size: 1` · `gradient_accumulation_steps: 32` ·
`gradient_checkpointing: true` · `max_seq_length: 3584` · the 4k-row Ozsoy generic sample ·
POLE-only continues.

Every one of these is held constant **so that model size is the only variable** across the
mistral-7B / qwen-32B / qwen-72B columns. That single sentence is what makes the Phase-11 scale
comparison defensible; a "while we're here" improvement to any of them silently destroys it. If
one must change (e.g. fp16 loss divergence), change only that one, and log it.

## Registry entry — `config/models.yaml`

```yaml
qwen2.5-72b:
  base: "Qwen/Qwen2.5-72B"                   # BASE, not -Instruct — same parity argument as 10.5
  target_modules: ["q_proj", "v_proj"]       # identical to qwen2.5-32b (Qwen2 attention names)
  dtype: "float16"                           # sm90 HAS bf16; fp16 kept for cross-model parity (11.1)
  load_in_4bit: true                         # inherited from 10.5's lock; 11.2 measures, does not re-decide
```

Cached already: 37 shards / 136 GiB in `$HF_HOME` (provenance recorded by 11.1).

## Fit-test — `kaya/111_qwen72b_fit_test.slurm`

Reuse `kaya/qwen_fit_test.py` with an additive `--model_key` (default `qwen2.5-32b`, so the
10.5 invocation is byte-identical). **Drop the 8-bit leg** — 10.5 settled precision, and an
8-bit 72B (~78 GiB) is of no interest. Legs: `load` → `generate` → `train` → `summary`, each a
separate process as 10.5 established. Measure and print:

1. **4-bit load footprint on one H100.** Expect ~41 GiB (72.7 B × 0.5 B/param + the untied
   fp16 `embed_tokens` and `lm_head`, 1.25 B params each). Record the real number — 11.4's
   device planning depends on it more than anything else here.
2. **One QLoRA train step** at batch 1 + GC on a real `data/pole_ext_sl_train.jsonl` row at
   seq 3584: peak VRAM + **s/micro-step**. The prediction from scaling 10.7's measured
   3.03 s/micro-step by parameters is **~6.8 s**; this leg replaces that estimate with a fact,
   and 11.3's budget table must be rebuilt from it.
3. **Batch-2 headroom probe** (`--tolerate_failure`): record whether it fits and at what peak.
   **Recorded as evidence only — do NOT adopt it.** Batch 1 is required by the parity clause;
   the measurement exists so the writeup can say the constraint was a choice, not a limit.
4. **One diverse-beam `k=5` SL generate**, latency recorded. 10.7 measured ~7 s/item at 32B on
   an H100; this sets 11.4's G1/G4 wall-clock budget.
5. **Three-co-located-load arithmetic for 11.4** — print `3 × measured_load_GiB` beside the
   93.6 GiB card size and state explicitly whether C3's SL + QG + AD fit on two cards under
   `experiments/build_condition3.py::_device_maps()` (which pins SL→`cuda:0`, QG **and** AD→`cuda:1`).
   At the predicted ~41 GiB each this is **~82 GiB of weights on card 1 before any KV cache**,
   i.e. it does **not** fit and 11.4 needs a third GPU. Confirm or refute with the real number.
6. **Recommendation block**: locked precision, GPUs needed for training vs inference vs e2e,
   and the per-adapter training extrapolation from leg 2.

## Acceptance criteria

1. `qwen2.5-72b` registry entry added; `build_llm` loads it on an H100 with **no change** to
   `pipeline/llm/huggingface.py` (or the change recorded as a deviation).
2. 4-bit load footprint and QLoRA train-step peak measured on one H100 and recorded in the
   tracker row, with the 1-GPU-per-training-job claim confirmed.
3. **s/micro-step measured** at batch 1 + GC; 11.3's budget table is rebuilt from it (the ~6.8 s
   figure in 11.3 is an estimate and must be replaced).
4. One diverse-beam `k=5` generate succeeds; latency recorded.
5. Leg 5 answers the 11.4 device question with a number: how many H100s the C3 e2e needs.
6. Offline suite green under `t2c` (a new registry key must not break the registry-enumerating
   tests); the 400/5 baseline holds.

## Handoff

11.3 trains six adapters at the measured throughput; 11.4 sizes its `--gres` from leg 5 and its
walltime from legs 2 and 4. The registry entry is the only onboarding artefact — every later
72B run is config-only.
