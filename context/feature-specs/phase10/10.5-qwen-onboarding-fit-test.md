# 10.5 — Qwen2.5-32B Onboarding + Precision Fit-Test

**Modules:** `config/models.yaml` (new `qwen2.5-32b` entry), `kaya/97_qwen_fit_test.slurm`
+ `kaya/qwen_fit_test.py` (new; GO/NO-GO probe). `pipeline/llm/huggingface.py` is expected to
be reused **unchanged** — Qwen2.5 is `Qwen2ForCausalLM`, which `AutoModelForCausalLM` loads
natively, and its arch is supported by the pinned `transformers<4.46` (config
`transformers_version: 4.43`). If a load quirk forces a loader change, that is a deviation →
decisions-log.
**Depends on:** 0.2 (`HuggingFaceLLM`, `build_llm`), 2.1 (`run_sft`/`build_model_inputs`).
**GPU** — must run on a **`v100-32gb`** node (k017–020), not a 16GB V100 (workflow §7).
**Consumed by:** 10.6 (training at the locked precision) and 10.7 (e2e).

---

## Objective

Onboard Qwen2.5-32B as a new local `model_key` and **empirically lock its precision (4-bit vs
8-bit) and `target_modules` on the real v100-32gb hardware** before spending days of GPU time
on training. This is the "decide after a fit-test" step the user asked for. Because Qwen2.5 is
a standard causal LM on a supported transformers, the feasibility risk is low — this is a
precision/memory measurement, not a go/no-go on whether the model runs at all (that risk was
what killed Qwen3.8-27B; see the Phase-10 planning discussion / decisions-log).

## Registry entry — `config/models.yaml`

```yaml
qwen2.5-32b:
  base: "Qwen/Qwen2.5-32B"                    # BASE, not -Instruct: parity with mistral7b (v0.3 base)
                                              # so C1 is an honest zero-shot base baseline and C2/C3
                                              # isolate the SFT effect. (If a strong C1 is wanted,
                                              # -Instruct is the alternative — record the choice.)
  target_modules: ["q_proj", "v_proj"]        # Qwen2 attention proj names; mirrors mistral7b's set
                                              # (fuller ["q_proj","k_proj","v_proj","o_proj"] is the
                                              # alternative — the fit-test confirms the names load)
  dtype: "float16"                            # Volta has no bf16 (also the bnb_4bit_compute_dtype)
  load_in_4bit: true                          # PLACEHOLDER — the fit-test confirms/overrides this
```

Adding this entry is a single-file change per the models.yaml contract (no code/spec change to
onboard a base). `predownload.py` must cache `Qwen/Qwen2.5-32B` on the login node first (the
compute nodes are offline — `kaya/README.md` §Gotchas).

## Fit-test — `kaya/qwen_fit_test.py` (run via `97_qwen_fit_test.slurm`, `--gres=gpu:2` on a v100-32gb node)

Measure and print, at minimum:

1. **Load VRAM at 4-bit** (`load_in_4bit: true`) — record per-GPU + total resident MiB. Expect
   ~16–18GB (fits one 32GB card).
2. **Load VRAM at 8-bit** (`load_in_8bit`) — record. Expect ~32GB (tight on one card; may span
   two). Note if it OOMs a single card.
3. **One QLoRA train step** at the locked precision: `build_model_inputs` on a real
   `data/pole_ext_sl_train.jsonl` row, `max_seq_length: 3584`, `per_device_train_batch_size: 2`
   + gradient checkpointing — one forward+backward+step, record **peak** VRAM, confirm no OOM.
4. **One diverse-beam SL generate** (`k=5`, the local SL decoding) via `probe_utils.generate_beams`
   or `SchemaLinker` — confirm it runs and record latency (32B beam search is slower; this
   informs the G4 wall-clock budget).
5. Print a **recommendation**: precision, whether 1 or 2 GPUs are needed for training vs
   inference, and the estimated per-adapter training time (extrapolate from the measured
   step time × the 10.2 mixed-file row count × epochs).

Then set `load_in_4bit`/`dtype` in the registry entry to the locked choice and record the
measured numbers in the tracker row.

---

## Acceptance criteria

1. `qwen2.5-32b` registry entry added; `build_llm` loads it on a v100-32gb node with **no code
   change** to `pipeline/llm/huggingface.py` (or the required change recorded as a deviation).
2. VRAM measured at 4-bit **and** 8-bit; precision locked in the registry with the numbers in
   the tracker row; the 1-vs-2-GPU need for training and for inference stated.
3. One QLoRA step + one diverse-beam `k=5` generate both succeed at the locked precision with
   no OOM; step latency + generate latency recorded (feeds the 10.6/10.7 time budgets).
4. Offline suite still green (adding a registry key must not break `tests/` — e.g.
   `test_condition_builders`/`test_run_evaluation` that enumerate the registry).

## Handoff

10.6 trains Qwen adapters at the locked precision/target_modules; 10.7 runs the e2e. The
registry entry is the single onboarding artefact — any later Qwen run is config-only.
