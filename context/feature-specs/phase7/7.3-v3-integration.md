# 7.3 — v3 Pipeline Integration (config-switched, v2 untouched)

**Modules:** `pipeline/schema.py` (additive), `pipeline/entity_lookup/registry.py` +
`span_extractor.py` (additive), `pipeline/ambiguity/prompts.py` +
`pipeline/disambiguator/prompts.py` (additive v3 variants), `config/pipeline.yaml`,
`experiments/run_evaluation.py` (version plumbing), `experiments/entropy_probe.py` /
`diversity_penalty_sweep.py` (version-tagged artefact paths).
**Depends on:** 7.1, 7.2, and the existing 0.3 / 3.2 / 3.4 / 3.5 / 5.4 contracts.
**Consumed by:** 7.4 (v3 schema block in SFT prompts), 7.5 (all runs).

---

## Objective

Make the whole pipeline run against the v3 dataset **by config only**, with the v2 path
byte-identical to today. Everything hardcoding v2 specifics gets a v3 variant selected
by one config key; no shared type or public signature changes.

## The one switch

`config/pipeline.yaml` gains:

```yaml
dataset_version: v3        # v2 | v3 — selects schema repr, entity registry, prompts
benchmark: data/benchmark-v3.json
results_tag: v3            # suffixed into results artefact names
```

`run_evaluation.main` reads `dataset_version` and threads the right objects through the
existing 5.3 builder signatures. Default when the key is absent: `v2` (back-compat).

## Touch points (inventory — this is the step's whole scope)

1. **Schema repr (0.3):** add `build_pole_v3_schema_repr() -> SchemaRepr` (6 labels, 11
   paths, temporal-edge property lists per 7.1) alongside the untouched
   `build_pole_schema_repr()`. One selector helper
   `build_schema_repr(version: str) -> SchemaRepr` maps `"v2"`/`"v3"`; consumers keep
   receiving a `SchemaRepr` — no consumer change.
2. **Entity registry (3.2):** v3 registry = Person / Case / Location searchable
   (`Organisation` no longer exists). Add a version-keyed registry lookup; the v2
   `ENTITY_REGISTRY` constant stays exported (3.2's contract). `_KNOWN_SUBURBS` gains
   the v3 suburb list (superset is fine — it is a recall aid).
3. **AD prompts (3.4):** `AD_SYSTEM_PROMPT` embeds a curated v2 schema + few-shots
   naming v2 entities. Author `AD_SYSTEM_PROMPT_V3` (same structure/taxonomy, v3 schema
   block, few-shots re-grounded in v3 seed data); `ambiguity_detector` gets the prompt
   via the existing injection path — selection happens in the condition builders from
   `dataset_version`, not inside the detector.
4. **Disambiguator prompts (3.5):** same treatment (`DIS_SYSTEM_PROMPT_V3`, 3 few-shots
   re-grounded in v3; e.g. the temporal example's `OWNS {active:true}` carries over
   unchanged since v3 keeps that edge).
5. **Results/caches versioned:** `_persist` (5.4) writes
   `results/tables_{model_key}_{results_tag}.md` / `metrics_{model_key}_{results_tag}.json`
   (empty tag → today's names, so v2 artefacts are untouched); 2.2/2.3 sweep + probe
   artefacts and the beam cache gain the same tag
   (`results/beams_{model_key}_{tag}.jsonl` etc., extending the 2026-06-30 model-keyed
   scheme).
6. **Neo4j target:** `config/pipeline.yaml` documents that v3 runs require the
   `kaya/70_neo4j_v3.slurm` graph (separate data dir), not the v2 one.

Explicitly **not** in scope: benchmark loader (0.4, already path-driven), orchestrator
(5.2), QG prompts (1.3 — schema block is a parameter already), metrics (4.2),
`pipeline/types.py`.

---

## Acceptance criteria

1. Full offline suite green; **v2 regression guard:** with `dataset_version: v2` (or
   the key absent), the SL/QG/AD/Dis prompts and all artefact paths are byte-identical
   to pre-7.3 behaviour (test compares rendered prompts + resolved paths).
2. `build_pole_v3_schema_repr()` counts: 6 labels, 11 paths; serialised block contains
   one cypher line per path and the temporal properties (mirror of 0.3's tests).
3. With `dataset_version: v3`, the resolved run config points at the v3 benchmark, v3
   schema repr, v3 registry, v3 prompts, and tagged artefact paths — asserted without
   loading any model.
4. On Kaya (live v3 Neo4j, no GPU): `EntityCache.load` against the v3 graph returns
   exactly the 7.1 volumes for Person/Case/Location and the duplicate-name seeds
   produce ≥2 fuzzy candidates for a known colliding mention (the entity-entropy
   precondition v2 never satisfied).

## Handoff

7.4 imports `build_pole_v3_schema_repr` for SFT prompt rendering. 7.5 runs everything
through `dataset_version: v3` + `results_tag: v3`. The v2 configuration remains fully
runnable for baseline comparison in the dissertation.
