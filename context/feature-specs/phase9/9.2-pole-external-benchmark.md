# 9.2 — External POLE Benchmark: Cypher Authoring + Validation Harness

**Modules/artefacts:** `data/benchmark-pole-external.json` (new), `experiments/validate_benchmark.py`
(extended — additive `BenchmarkProfile`), `experiments/pole_query.py` (new — ad hoc query CLI).
**Depends on:** 9.1 (confirmed skeleton), 0.4 (`load_benchmark`, unchanged), 3.7/3.8 (CyVer +
`db_executor`, reused as-is). **Live external POLE Neo4j required** — per `ai-workflow-rules.md`
§7, run the validation for real in the implementing session.
**Consumed by:** 9.3 (config points at this file for the local run).

---

## Objective

Turn the 9.1 skeleton (100 items, all `data_support: CONFIRMED`, no Cypher) into the canonical
`data/benchmark-pole-external.json` by authoring `cypher_default` and per-interpretation Cypher for
every item, and generalize the existing 7.2 validation harness so it proves — executably, against
the live graph — that every gold query runs non-empty and every ambiguous item's interpretations
are pairwise distinct. This is the same discipline 7.2 applied to the synthetic v3 graph, applied
here to a real graph the student did not build.

**Ship a small ad hoc query tool first.** Authoring 100 items against a graph this large (61.5k
nodes) requires many exploratory verification queries beyond what 9.1 already ran — the same kind
of "does this tie/divergence/count actually hold" check used to resolve I10/I11/I15/T20 in 9.1.
Rather than the manual paste-into-Neo4j-Browser loop used so far, `experiments/pole_query.py`
gives a scriptable, testable path to run one-off Cypher and see the result immediately, using the
same connection contract the validation harness already uses.

## Connection contract (unchanged from 3.2+/7.2 — no new code needed for this part)

`validate_benchmark.py`'s existing env-var defaults already match the live instance as described
by the user:

| Env var | Default in code | User's instance |
|---|---|---|
| `NEO4J_URI` | `bolt://localhost:7687` | `bolt://localhost:7687` |
| `NEO4J_USERNAME` | `neo4j` | `neo4j` |
| `NEO4J_DATABASE` | `neo4j` | `neo4j` |
| `NEO4J_PASSWORD` | *(required, no default — fails loud if unset)* | `changeme` |

So running against this instance needs **only** `export NEO4J_PASSWORD=changeme` in the shell —
no URI/user/database override, no code change, and (per `code-standards.md`) the password is
never committed to a config file. `experiments/pole_query.py` (below) reuses this exact contract
so both tools point at the same instance with zero duplicated connection logic.

## Item contract (unchanged from 7.2 — loader compatibility is the point)

Identical JSON shape to `benchmark-v3.json`, loadable by `load_benchmark` (0.4) with **zero code
change**: `question_id`, `question`, `num_hops`, `is_ambiguous`,
`ambiguity_type ∈ {schema, entity, intent, temporal, null}`, `default_interp`, `cypher_default`,
`interpretations: [{interp, cypher}]` (empty list for unambiguous items). The skeleton's
`planned_interpretations`/`data_support` fields do **not** carry into the final file.

Authoring rules:
- Every Cypher (default + interpretations) uses **only** the real POLE-external schema from 9.1 /
  `docs/neo4jpole.md` — 11 node labels, 17 relationship types, the real property names (`nhs_no`,
  `surname`, `name`, `badge_no`, `rank`, `areaCode`, `call_date`, `call_time`, etc.). This graph's
  labels/properties are **not** the synthetic v3 schema (`Person.person_id`, `Incident`, `Case`, …)
  — do not mix them up, exactly as flagged in the 9.1 handoff.
- Target ≤3 relationship hops per query, matching the project's existing convention
  (`ai-workflow-rules.md`, 7.2). If an item's `data_support` genuinely requires more (e.g. a
  multi-postcode-hop area lookup), do not silently author a 4+ hop query — flag it and record the
  decision in `decisions-log.md`, the same escalation pattern already used for the 9.1 flagged
  items.
- Ambiguous items: 2–4 interpretations (this skeleton's real ties go up to 4-way, e.g. I10), each
  with its own Cypher; `cypher_default` is the documented default reading.
- Single-line Cypher, real whitespace (the executor convention 3.8/7.2 already expect).
- Question text unique across the file.
- Reuse the concrete facts already gathered rather than re-querying where possible — the raw data
  block in `decisions-log.md`'s 2026-08-02 design row (officer badge numbers, area total/violent
  counts, per-day M1/BL1/citywide counts, KNOWS-family pairs, PARTY_TO+INVOLVED_IN crime IDs,
  duplicate-surname clusters) already grounds most items; use `pole_query.py` for anything not
  already covered there.

## `experiments/pole_query.py` — ad hoc query CLI (new)

A thin, testable wrapper around the existing `pipeline.execution.db_executor`, for one-off
exploratory/verification queries during authoring (and later, spot-checks during 9.3's run) — not
a new execution engine.

```
python -m experiments.pole_query "MATCH (o:Officer {rank:'Sergeant'}) RETURN o.surname, o.name, count(*) AS n ORDER BY n DESC LIMIT 10"
```

- Reads the same `NEO4J_URI` / `NEO4J_USERNAME` / `NEO4J_PASSWORD` / `NEO4J_DATABASE` env
  contract as `validate_benchmark.py` (factor the driver-opening helper into a small shared
  function both modules import, rather than duplicating `_open_driver`).
- Runs the query via `db_executor` (3.8) — same managed-read-transaction, same
  `ExecutionResult` contract, same server-side timeout.
- Prints: on success, each result row as one JSON line (`json.dumps(record, default=str)` — the
  executor already reduces nodes/relationships to plain property dicts) plus a trailing
  `# n_rows=<N> elapsed_ms=<T>` summary line; on failure, the `ExecutionResult.error` message and
  a non-zero exit code.
- Optional `--limit N` truncates printed rows (the query itself is run as written — this only
  caps display, so a query author still sees the true row count in the summary line).
- No write capability, no query rewriting, no retry — deliberately minimal; it exists to remove
  friction from the authoring loop, not to become a second `db_executor`.

## Validation harness — `experiments/validate_benchmark.py` (additive generalization)

Today the module hardcodes v3-specific constants at file scope
(`V3_LABELS`, `V3_REL_TYPES`, `EXPECTED_DISTRIBUTION`, `EXPECTED_TOTAL`, `MAX_HOPS`,
`MIN_COVERAGE`) and its docstring overstates version-agnosticism — the gates that actually read
those constants (`gate_distribution`, `gate_coverage`) are not parameterized. Generalize via a
`BenchmarkProfile`:

```python
@dataclass
class BenchmarkProfile:
    name: str
    rel_types: list[str]          # closure target for gate 8 (coverage)
    expected_distribution: dict[Optional[str], int]   # gate 2
    expected_total: int                                # gate 2
    max_hops: int = 3                                  # gate 7
    min_coverage: int = 3                               # gate 8
```

- `V3_PROFILE` reproduces today's module-level constants **byte-identically** (regression guard —
  `python -m experiments.validate_benchmark --benchmark data/benchmark-v3.json` with no `--profile`
  flag must behave exactly as before).
- `POLE_EXTERNAL_PROFILE`: `rel_types` = the 17 types from 9.1 (`docs/neo4jpole.md`);
  `expected_distribution = {None: 20, "schema": 20, "entity": 20, "intent": 20, "temporal": 20}`;
  `expected_total = 100`; `max_hops = 3`; **`min_coverage = 1`** (relaxed from v3's 3 — several real
  relationship types are structurally rare in this graph, e.g. `PARTY_TO` has only 55 edges total
  and `FAMILY_REL` 155, so a ≥3-item bar used for the *designed* synthetic v3 schema is not
  realistic here without contriving repetitive questions; record any relationship type that ends
  up at 0 coverage in `decisions-log.md` with the reason, rather than silently accepting a gap).
- `gate_distribution`, `gate_coverage`, and `validate()` take a `profile: BenchmarkProfile`
  parameter (default `V3_PROFILE`, preserving today's call signature for existing callers/tests).
- CLI gains `--profile {v3,pole_external}` (default `v3`).
- Gates 3–6 (syntax/schema-closure/non-empty/divergence) are **already graph-agnostic** — they
  route through CyVer's live-introspecting `SchemaValidator`/`PropertiesValidator` and
  `db_executor` against whatever graph the connection actually points at, so they need no change
  for a new schema. Only gates 2 and 8 read the hardcoded inventory/distribution.

Report path convention: `results/benchmark_pole_external_validation.json` (mirrors
`results/benchmark_v3_validation.json`).

## Acceptance criteria

1. **Offline (no DB):** `V3_PROFILE`-driven `gate_distribution`/`gate_coverage` produce identical
   pass/fail/detail output to the pre-9.2 hardcoded functions on the existing v3 test fixtures
   (regression guard). `POLE_EXTERNAL_PROFILE`-driven versions catch a wrong 100-item distribution
   and a relationship type with 0 coverage on a small hand-built fixture.
2. **Offline:** `pole_query.py`'s row-printing/summary logic is unit-tested against a fake
   `ExecutionResult` (success and failure paths) without opening a real driver.
3. **Live** (instance running at `bolt://localhost:7687`, database `neo4j`, user `neo4j`,
   `NEO4J_PASSWORD=changeme`): the full 8-gate harness passes green over
   `data/benchmark-pole-external.json` with `--profile pole_external`; the report is committed to
   `results/benchmark_pole_external_validation.json`.
4. `load_benchmark("data/benchmark-pole-external.json")` + `ambiguous_items` + `items_by_type`
   return the expected 100 / 80 / {20,20,20,20} splits.
5. Any authoring decision that deviates from the rules above (hop cap exceeded, a relationship
   type left uncovered, an interpretation count outside 2–4) is recorded in `decisions-log.md`
   with reasoning, not silently accepted.

## Handoff

`data/benchmark-pole-external.json` is canonical **once criterion 3 passes** (mirrors
`ai-workflow-rules.md` §6's v3 canonicalization rule). 9.3 points the local-run config at this
file and wires the schema representation / entity registry / AD-Dis prompts needed to actually run
the pipeline against it.
